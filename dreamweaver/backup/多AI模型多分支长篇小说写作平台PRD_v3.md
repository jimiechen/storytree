# 第 1 章 产品概述

## 1.1 产品背景

长篇小说创作是一项复杂的智力劳动，涉及世界观构建、角色塑造、情节编排、伏笔埋设、主题表达等多个维度。传统的写作工具（如 Word、Scrivener）主要解决"排版"和"组织"问题，但无法帮助作者处理创作过程中最核心的挑战——**如何在数十万字的篇幅中保持叙事一致性、情节张力和文学品质**。

随着大语言模型（LLM）技术的快速发展，AI 已经具备了辅助文学创作的能力。然而，现有的 AI 写作工具存在明显不足：

- **单一模型局限**：大多数工具只支持一个 AI 模型，无法利用不同模型的优势
- **线性叙事限制**：不支持分支叙事和"假设性写作"（如"如果让角色走另一条路会怎样？"）
- **缺乏深度理解**：AI 无法理解整部小说的世界观、角色关系和情节脉络
- **被动响应模式**：AI 只能在用户提问时响应，无法主动提供创作建议

DreamWeaver 平台旨在解决这些问题，为长篇小说创作者提供一个真正智能的创作环境。

## 1.2 产品愿景

**打造全球首个多AI模型协作、多分支叙事、智能代理驱动的长篇小说创作平台。**

我们的愿景是让每一位小说创作者都能拥有一个由多个 AI 专家组成的"虚拟写作团队"：

- **多模型协作**：不同 AI 模型各司其职——GPT 擅长创意发散，Claude 擅长长文本连贯性，Gemini 擅长知识检索，本地模型保障隐私
- **分支叙事自由**：像 Git 一样管理故事线，随时创建"如果"分支，探索不同的叙事可能性
- **深度世界观理解**：AI 真正理解你的小说世界，记住每一个角色、每一条伏笔、每一个设定
- **智能代理驱动**：借鉴 Claude Code 的 REPL+QueryEngine+Tool 三层架构，打造小说创作领域的智能代理系统
- **创作全流程覆盖**：从灵感萌芽到完稿发布，提供全链路支持

## 1.3 目标用户

### 1.3.1 核心用户

## 1.4 核心问题

基于用户调研和竞品分析，我们识别出以下核心问题：

### P1：多模型能力无法统一利用
**现状**：不同 AI 模型各有优势（GPT 创意强、Claude 长文本好、Gemini 知识广），但创作者需要在不同工具间切换。
**影响**：创作流程断裂，上下文丢失，效率低下。

### P2：长篇小说的一致性维护困难
**现状**：当小说超过 10 万字时，角色性格、世界观设定、伏笔线索极易出现矛盾。
**影响**：作品质量下降，读者体验受损，修改成本极高。

### P3：分支叙事缺乏工具支持
**现状**：作者想要探索不同的情节走向时，只能手动复制粘贴，版本管理混乱。
**影响**：创作自由度受限，"写错"的恐惧阻碍创作。

### P4：AI 对小说全局理解不足
**现状**：现有 AI 工具的上下文窗口有限，无法理解整部小说的情节脉络和角色关系。
**影响**：AI 建议往往脱离上下文，缺乏实用价值。

### P5：创作灵感难以持续
**现状**：长篇创作过程中，作者经常遇到"卡文"（写作瓶颈），缺乏有效的灵感激发机制。
**影响**：作品烂尾率高，创作体验差。

### P6：协作与反馈机制缺失
**现状**：小说创作通常是孤独的，缺乏实时的协作编辑和读者反馈整合机制。
**影响**：作品质量提升慢，读者粘性低。

### P7：缺乏智能代理能力——AI 只能被动响应，无法主动规划、自主执行、记忆积累
**现状**：现有 AI 写作工具本质上是对话式问答，AI 只能在用户主动提问时才给出回应，无法像真正的写作助手那样持续跟踪创作进度、主动发现潜在问题、积累创作记忆。
**影响**：作者需要反复向 AI 解释背景信息，AI 无法提供前瞻性建议，创作效率无法实现质的飞跃。

## 1.5 产品定位

DreamWeaver 定位为**面向长篇小说创作者的 AI 原生创作平台**，而非简单的"AI 写作助手"。

**核心差异化**：
1. **多模型编排**：不是"一个 AI 帮你写"，而是"一群 AI 专家协作帮你写"
2. **分支叙事**：不是"线性写作"，而是"探索式创作"
3. **智能代理**：不是"你问 AI 答"，而是"AI 主动参与创作全流程"
4. **深度理解**：不是"基于当前段落建议"，而是"理解整部小说全局"

**一句话定位**：
> DreamWeaver —— 你的 AI 虚拟写作团队，让长篇小说创作从孤独的苦旅变成协作的旅程。

# 第 2 章 市场分析

## 2.1 竞品分析

### 2.1.1 直接竞品

| 竞品 | 优势 | 劣势 | 与 DreamWeaver 差异 |
|------|------|------|---------------------|
| **NovelAI** | 图像生成、故事模式丰富 | 单一模型、无分支叙事、英文为主 | 多模型协作 + 分支叙事 + 中文优化 |
| **Sudowrite** | 故事引擎、自动续写 | 价格高、无世界观管理、无协作 | 世界观深度管理 + 多分支 + 开放 API |
| **Jasper** | 品牌知名度、营销内容强 | 非小说专用、无长篇支持 | 专注长篇小说 + 深度叙事理解 |
| **ChatGPT/Claude 直接使用** | 免费/低价、通用性强 | 无小说专用功能、无版本管理 | 专业小说工具链 + 多分支 + 一致性维护 |

### 2.1.2 间接竞品

| 竞品 | 优势 | 劣势 |
|------|------|------|
| **Scrivener** | 成熟的写作组织工具 | 无 AI 能力、学习曲线陡 |
| **Notion + AI** | 灵活的知识管理 | 非写作专用、AI 能力浅 |
| **语雀/飞书文档** | 中文生态好 | 无小说专用功能 |

### 2.1.3 竞品定位图

```
                    AI 能力强
                       ↑
                       │
    Claude/ChatGPT     │     DreamWeaver（目标位置）
    直接使用            │
                       │
    ───────────────────┼──────────────────→ 小说专用性强
                       │
    NovelAI            │     Scrivener
                       │
    Sudowrite          │     Notion + AI
                       │
                    AI 能力弱
```

## 2.2 市场机会

### 2.2.1 市场规模

- **全球 AI 写作工具市场**：2025 年预计达到 32 亿美元，CAGR 28%
- **中国网文市场**：2025 年预计达到 400 亿元人民币
- **AI 辅助创作渗透率**：目前约 15%，预计 2027 年达到 45%

### 2.2.2 趋势分析

1. **AI 模型能力持续提升**：GPT-5、Claude 4 等新模型将大幅提升长文本理解和生成能力
2. **创作者对 AI 接受度提高**：从"抵触"到"拥抱"的转变正在加速
3. **多模型生态成熟**：API 成本下降，模型选择更加丰富
4. **内容平台需求增长**：网文平台、出版社对 AI 辅助创作的需求日益强烈

### 2.2.3 时机窗口

- **技术窗口**：多模态大模型 + RAG + Agent 技术的成熟，使得深度小说辅助成为可能
- **市场窗口**：AI 写作工具市场尚未出现明确的"长篇小说专用"领导者
- **用户窗口**：新一代创作者（Z 世代）对 AI 工具的接受度极高

## 2.3 差异化策略

### 2.3.1 三大护城河

1. **多模型编排引擎**：构建独特的多 AI 模型协作框架，这是纯工具类产品难以复制的
2. **分支叙事系统**：将 Git 的版本管理理念引入小说创作，形成独特的创作范式
3. **智能代理系统**：借鉴 Claude Code 的代理架构，打造真正"懂你小说"的 AI 助手

### 2.3.2 竞争策略

| 阶段 | 策略 | 目标 |
|------|------|------|
| **进入期** | 聚焦中文网文作者，以"多模型+分支叙事"切入 | 建立初始用户群 |
| **成长期** | 开放 API，构建插件生态，吸引开发者 | 扩大平台效应 |
| **成熟期** | 打造"创作社区 + AI 工具 + 出版对接"闭环 | 构建生态壁垒 |

# 第 4 章 产品原则

## 4.1 设计原则

### DP1：AI 是助手，不是替代者
- AI 的角色是辅助创作者，而非替代创作者
- 所有 AI 生成的内容都需要经过创作者确认
- 创作者始终拥有最终决定权

### DP2：透明可控
- 用户清楚知道 AI 在做什么、为什么这么做
- 所有 AI 操作可审计、可撤销
- AI 的决策逻辑可解释

### DP3：渐进增强
- 基础功能不依赖 AI 也能使用
- AI 能力是"加分项"，不是"必需项"
- 用户可以自主选择 AI 参与的程度

### DP4：数据主权
- 用户的创作数据完全归用户所有
- 支持数据导出和完全删除
- AI 模型调用不泄露用户数据

## 4.2 体验原则

### EP1：沉浸式写作体验
- 写作界面简洁、无干扰
- AI 交互不打断写作心流
- 支持"专注模式"

### EP2：即时反馈
- AI 响应时间 < 2 秒（简单任务）
- 操作反馈即时可见
- 后台任务进度透明

### EP3：容错设计
- 所有操作支持撤销
- 分支系统确保"写错不可怕"
- 自动保存 + 版本快照

### EP4：学习曲线友好
- 新手引导清晰
- 功能渐进式暴露
- 提供"快速上手"和"深度使用"两条路径

# 第 5 章 核心功能规划

## 5.1 模块一：AI 写作引擎

### 5.1.1 多模型管理

**功能描述**：支持接入和管理多个 AI 模型，用户可以根据创作需求选择最合适的模型。

**支持的模型**：

| 模型 | 提供商 | 优势 | 适用场景 |
|------|--------|------|----------|
| GPT-4o | OpenAI | 创意发散、对话生成 | 角色对话、创意头脑风暴 |
| Claude 4 | Anthropic | 长文本连贯性、逻辑推理 | 长篇续写、一致性检查 |
| Gemini 2.0 | Google | 知识检索、多语言 | 背景设定、知识查询 |
| DeepSeek V3 | DeepSeek | 中文理解、性价比高 | 中文写作、日常辅助 |
| Qwen 3 | 阿里云 | 中文创作、文化理解 | 古风/仙侠题材 |
| Llama 4 | Meta | 开源、可本地部署 | 隐私敏感场景 |
| GLM-5 | 智谱AI | 中文优化、指令遵循 | 通用中文写作 |

**模型路由策略**：

```
用户请求 → 意图识别 → 模型路由器 → 选择最优模型
                              │
                              ├── 创意生成 → GPT-4o / Claude 4
                              ├── 长文续写 → Claude 4 / DeepSeek V3
                              ├── 知识查询 → Gemini 2.0
                              ├── 中文优化 → Qwen 3 / GLM-5
                              └── 隐私模式 → Llama 4（本地）
```

### 5.1.2 AI 写作模式

| 模式 | 描述 | 适用场景 |
|------|------|----------|
| **续写模式** | AI 根据上下文自动续写 | 日更、快速产出 |
| **扩写模式** | 对简短描述进行扩展 | 大纲→正文、场景细化 |
| **改写模式** | 保持原意但改变表达方式 | 风格调整、润色 |
| **对话模式** | 与 AI 讨论创作方向 | 灵感探索、问题解决 |
| **审查模式** | AI 分析文本质量 | 自我审查、质量提升 |
| **翻译模式** | 多语言翻译 | 跨语言创作 |

## 5.2 模块二：多分支叙事系统

### 5.2.1 分支模型

**核心概念**：借鉴 Git 的版本控制理念，为小说创作提供分支管理能力。

```
main（主线）
  │
  ├── chapter-1
  │     ├── scene-1-1
  │     ├── scene-1-2
  │     └── scene-1-3
  │
  ├── branch/alternate-ending（备选结局分支）
  │     ├── chapter-1（继承自 main）
  │     ├── chapter-2（修改版）
  │     └── chapter-3（新结局）
  │
  └── branch/romance-subplot（感情线分支）
        ├── chapter-1（继承自 main）
        ├── chapter-2（加入感情线）
        └── chapter-3（感情线发展）
```

**分支类型**：

| 类型 | 描述 | 用途 |
|------|------|------|
| **主线（main）** | 小说的"官方"版本 | 最终发布的内容 |
| **探索分支** | 尝试不同的情节走向 | 创作实验 |
| **角色视角分支** | 从不同角色视角重写 | 丰富叙事层次 |
| **时间线分支** | 改变关键事件的时间点 | 探索蝴蝶效应 |
| **风格分支** | 用不同风格重写 | 风格实验 |

### 5.2.2 分支操作

| 操作 | 描述 | 类比 Git |
|------|------|----------|
| **创建分支** | 从任意节点创建新分支 | `git branch` |
| **切换分支** | 在不同分支间切换 | `git checkout` |
| **合并分支** | 将分支内容合并回主线 | `git merge` |
| **对比差异** | 查看两个分支的差异 | `git diff` |
| **分支可视化** | 图形化展示分支关系 | `git log --graph` |
| **Cherry-pick** | 从分支中选取特定章节/场景 | `git cherry-pick` |

### 5.2.3 分支冲突处理

当合并分支时可能出现冲突，系统提供以下处理方式：

```
冲突检测 → 冲突标记 → 用户选择 → 冲突解决
                │
                ├── 保留 A 版本
                ├── 保留 B 版本
                ├── AI 辅助合并（推荐）
                └── 手动编辑
```

### 5.2.4 分支元数据

每个分支维护以下元数据：

```json
  "createdAt": "2026-01-15T10:00:00Z",
  "updatedAt": "2026-01-20T15:30:00Z",
  "wordCount": 45000,
  "status": "active",
  "tags": ["dark", "experimental"]
}
```

## 5.10 模块八：智能代理系统（P0）

> 本模块深度借鉴 Claude Code 的 KAIROS/PROACTIVE/COORDINATOR_MODE 架构设计，将软件工程领域的智能代理理念引入小说创作领域。

### 5.10.1 代理架构

**三层架构设计**：

借鉴 Claude Code 的核心架构，DreamWeaver 的智能代理系统采用 **REPL（交互循环）+ QueryEngine（查询引擎）+ Tool（工具系统）** 三层架构。

```
┌─────────────────────────────────────────────────────────────┐
│                    REPL（交互循环层）                         │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  Read → Think → Act → Observe → Think → ...        │    │
│  │                                                     │    │
│  │  • 接收用户输入/系统事件                              │    │
│  │  • 调用 QueryEngine 进行推理                          │    │
│  │  • 通过 Tool 系统执行操作                              │    │
│  │  • 观察执行结果，决定下一步                            │    │
│  │  • 循环直到任务完成                                   │    │
│  └─────────────────────────────────────────────────────┘    │
├─────────────────────────────────────────────────────────────┤
│                  QueryEngine（查询引擎层）                    │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  • 意图识别与任务分解                                 │    │
│  │  • 多步推理与规划                                    │    │
│  │  • 上下文检索与整合（RAG + Memory）                   │    │
│  │  • 工具选择与参数生成                                 │    │
│  │  • 结果评估与决策                                    │    │
│  └─────────────────────────────────────────────────────┘    │
├─────────────────────────────────────────────────────────────┤
│                    Tool（工具系统层）                         │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  写作工具：续写/改写/扩写/缩写/翻译                    │    │
│  │  检索工具：世界观查询/角色查询/伏笔查询/全文搜索        │    │
│  │  分析工具：一致性检查/节奏分析/质量评估/风格分析        │    │
│  │  管理工具：章节管理/分支操作/版本控制/标签管理          │    │
│  │  记忆工具：记忆存储/记忆检索/记忆压缩/记忆清理          │    │
│  │  系统工具：文件读写/配置管理/钩子触发/通知发送          │    │
│  └─────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

**REPL 循环详细流程**：

```
1. READ（读取）
   │  读取用户输入、系统事件、定时任务触发
   │
2. THINK（思考）
   │  QueryEngine 分析意图，制定执行计划
   │  - 需要什么信息？→ 调用检索工具
   │  - 需要什么操作？→ 选择合适工具
   │  - 操作顺序？→ 生成执行计划
   │
3. ACT（执行）
   │  按计划调用 Tool 系统执行操作
   │  - 单工具调用或工具链
   │  - 每次调用通过队列串行执行
   │
4. OBSERVE（观察）
   │  收集执行结果
   │  - 工具返回值
   │  - 错误信息
   │  - 状态变化
   │
5. THINK（再思考）
   │  评估结果是否满足目标
   │  - 满足 → 输出结果给用户
   │  - 不满足 → 回到 THINK 或 ACT
   │  - 需要用户确认 → 暂停等待
   │
6. 循环直到任务完成或需要用户介入
```

### 5.10.2 主动模式（Proactive Mode）

借鉴 Claude Code 的 PROACTIVE_MODE，AI 可以在后台持续工作，不再只是被动等待用户指令。

**主动模式行为**：

| 行为类型 | 描述 | 触发条件 |
|----------|------|----------|
| **一致性巡检** | 自动检查新写入内容与已有设定的一致性 | 每次保存后 |
| **知识库更新** | 自动从新内容中提取设定、角色变化等信息 | 检测到新设定时 |
| **写作建议** | 基于当前创作状态主动提供建议 | 空闲时或检测到问题时 |
| **伏笔提醒** | 检查即将到期未回收的伏笔 | 接近预期回收章节时 |
| **节奏预警** | 分析当前章节的叙事节奏，预警异常 | 连续 N 章节奏相似时 |
| **角色状态同步** | 更新角色在故事中的当前状态 | 角色经历重大事件后 |

### 5.10.3 协调器模式（Coordinator Mode）

| **情节专家** | 情节设计、冲突构建、节奏把控 | Claude 4 |
| **风格专家** | 文学品质、修辞优化、语言美感 | GPT-4o |
| **设定专家** | 世界观一致性、设定查询、逻辑校验 | Gemini 2.0 |
| **读者模拟** | 模拟读者反应、预测阅读体验 | DeepSeek V3 |

**协调器工作流程**：

```
用户请求："帮我完善第 8 章的战斗场景"

┌─────────────────────────────────┐
│       主编排 AI（Coordinator）     │
│                                 │

│     ┌──────┬──────┬──────┬──────┐│

│     │ 专家  │ 专家  │ 专家  │ 专家  ││
│     └──┬───┴──┬───┴──┬───┴──┬───┘│
│        │      │      │      │    │

│  3. 收集各专家结果               │
│                                 │
```

### 5.10.4 子代理系统

支持创建子代理处理独立任务，子代理可以并行执行，大幅提升复杂任务的效率。

**子代理创建**：

```json
{
  "subAgent": {
    "taskId": "check-chapter-1-10-consistency",
    "parentAgent": "main-coordinator",
    "task": "检查第 1-10 章的角色一致性",
    "tools": ["characterQuery", "contentSearch", "consistencyCheck"],
    "model": "claude-4",
    "maxTurns": 20,
    "priority": "high",
    "status": "running"
  }
}
```

**子代理类型**：

| 类型 | 描述 | 示例 |
|------|------|------|
| **检查型** | 执行检查任务并返回报告 | 一致性检查、质量评估 |
| **生成型** | 生成内容供主编排选择 | 生成 3 个备选开头 |
| **分析型** | 分析数据并返回洞察 | 节奏分析、读者情绪分析 |
| **修改型** | 对内容进行修改（需确认） | 修复一致性问题 |

**并行执行管理**：

```
主代理
  │
  ├── 子代理 A：检查角色一致性 ──────→ 结果 A
  │
  ├── 子代理 B：检查时间线 ──────────→ 结果 B
  │
  ├── 子代理 C：检查伏笔状态 ────────→ 结果 C
  │
  └── 子代理 D：生成修改建议 ────────→ 结果 D
                                          │
                                          ▼
                                    主代理整合结果
```

**子代理生命周期**：

```
created → running → completed
                │
                ├── failed（失败，可重试）
                ├── cancelled（被取消）
                └── timeout（超时）
```

### 5.10.5 队列处理器

所有 AI 操作通过队列串行执行，避免并发冲突，确保系统稳定性。

**队列设计**：

```
┌─────────────────────────────────────────┐
│              操作队列（Queue）              │
│                                         │
│  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐      │
│  │Task1│→│Task2│→│Task3│→│Task4│→ ...  │
│  │高优先│ │高优先│ │中优先│ │低优先│      │
│  └─────┘ └─────┘ └─────┘ └─────┘      │
│                                         │
│  优先级：                                │
│  • CRITICAL：用户交互响应（立即执行）       │
│  • HIGH：主动模式检查（高优先）            │
│  • MEDIUM：子代理任务（中优先）            │
│  • LOW：后台分析任务（低优先）             │
│  • BACKGROUND：定时任务（后台执行）        │
└─────────────────────────────────────────┘
```

**队列特性**：

| 特性 | 描述 |
|------|------|
| **优先级调度** | 高优先级任务插队执行 |
| **速率限制** | 防止 API 调用过载 |
| **去重** | 相同任务不重复入队 |
| **超时处理** | 长时间运行的任务自动超时 |
| **结果缓存** | 相同输入的结果可复用 |
| **取消支持** | 可取消队列中的等待任务 |

## 5.11 模块九：钩子系统（P1）

> 本模块借鉴 Claude Code 的 20+ 生命周期钩子机制，为小说创作提供强大的事件驱动扩展能力。

### 5.11.1 钩子架构

**事件驱动 + 正则匹配 + stdin/stdout JSON 通信**：

```
┌──────────────────────────────────────────────────────────┐
│                    钩子执行管道                            │
│                                                          │
│  事件触发 → 正则匹配 → 钩子排序 → 钩子执行 → 结果处理      │

│      │                                                   │

│  │ Hook A  │ →  │ Hook B  │ →  │ Hook C  │ → 最终结果    │
│  │(内置)   │    │(用户)   │    │(插件)   │              │
│  └─────────┘    └─────────┘    └─────────┘              │
└──────────────────────────────────────────────────────────┘
```

| 钩子名称 | 触发时机 | 用途 |
|----------|----------|------|

| `preToolUse` | 工具调用前 | 参数验证、权限检查、速率限制 |

| 钩子名称 | 触发时机 | 用途 |
|----------|----------|------|
| `contentSave` | 内容保存时 | 自动备份、字数统计、变更通知 |
| `contentChange` | 内容变更时 | 实时检查、自动保存、协作同步 |
| `branchCreate` | 创建分支时 | 分支初始化、通知协作者 |
| `branchMerge` | 合并分支时 | 冲突预检、合并策略建议 |
| `branchSwitch` | 切换分支时 | 上下文切换、状态保存/恢复 |
| `characterUpdate` | 角色信息更新时 | 一致性检查、关系图谱更新 |
| `worldSettingChange` | 世界观设定变更时 | 影响分析、关联内容标记 |

### 5.11.5 钩子动作类型

| 动作类型 | 描述 | 使用场景 |
|----------|------|----------|
| `allow` | 允许操作继续 | 默认行为 |
| `deny` | 阻止操作执行 | 内容安全过滤、权限控制 |
| `modify` | 修改操作参数 | 提示词注入、参数调整 |
| `inform` | 仅通知，不影响操作 | 日志记录、统计分析 |

**动作优先级**：

```
deny > modify > allow > inform

如果多个钩子返回不同动作：
- 任一钩子返回 deny → 操作被阻止
- 存在 modify → 使用最后一个 modify 的结果
- 全部 allow/inform → 操作正常执行
```

### 5.13.3 稀有度分级

| 稀有度 | 概率 | 属性加成 | 特殊能力 | 视觉效果 |
|--------|------|----------|----------|----------|
| **Common（普通）** | 60% | 无 | 基础建议 | 标准外观 |

| **Legendary（传说）** | 1% | +50% 全属性 | 创作灵感爆发 | 全身特效 |

### 5.13.4 确定性生成

使用 userId 的 hash 值作为种子，通过 Mulberry32 PRNG 算法确定性地生成精灵，确保：

- 同一用户始终获得相同的初始精灵（防作弊）
- 精灵属性在生成时确定，不可通过刷新重置
- 不同用户获得不同的精灵

**生成算法**：

```javascript
function generateSprite(userId) {
  // userId hash → Mulberry32 PRNG seed
  const seed = hashString(userId);
  const rng = mulberry32(seed);

  // 确定物种
  const speciesRoll = rng();
  const species = determineSpecies(speciesRoll);

  // 确定稀有度
  const rarityRoll = rng();
  const rarity = determineRarity(rarityRoll);

  // 生成属性
  const attributes = {
    insight: baseStat(rng) + rarityBonus(rarity),
    patience: baseStat(rng) + rarityBonus(rarity),
    creativity: baseStat(rng) + rarityBonus(rarity),
    literacy: baseStat(rng) + rarityBonus(rarity),
    humor: baseStat(rng) + rarityBonus(rarity)
  };

  return { species, rarity, attributes };
}
```

### 5.14.5 Prompt Cache 优化

**缓存策略**：

```
请求 1：[缓存段 A] + [缓存段 B] + [动态段 C] + [用户输入]
         ↓ 缓存
请求 2：[缓存段 A] + [缓存段 B] + [动态段 D] + [用户输入]
         ↓ 命中缓存 A+B，只需计算 D
请求 3：[缓存段 A] + [缓存段 B] + [动态段 E] + [用户输入]
         ↓ 命中缓存 A+B，只需计算 E
```

**优化效果预估**：

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 平均 Prompt Tokens | 8000 | 3000（缓存命中时） | 62.5% 减少 |
| API 响应延迟 | 3.5s | 1.8s | 48.6% 减少 |
| API 成本（每请求） | $0.015 | $0.008 | 46.7% 减少 |
| Cache 命中率 | 0% | 70-85% | - |

```
│                                                             │
│  5. Prompt Cache 优化                                        │
│     ├── 静态段使用 global scope 缓存                          │
│     ├── 动态段按需缓存                                        │
│     └── 记录缓存命中率                                        │
└─────────────────────────────────────────────────────────────┘
```

### 6.3.4 上下文压缩策略

**四级渐进压缩流程**：

```
┌─────────────────────────────────────────────────────────────┐
│                    上下文压缩决策树                            │
│                                                             │
│  总 Token 数 < 预算的 80%                                    │
│  └── 无需压缩，直接使用                                       │
│                                                             │
│  总 Token 数 > 预算的 80%                                    │
│  └── Level 1: 微压缩                                        │
│      ├── 压缩单条超长记忆（>500 tokens）                      │
│      ├── 提取关键信息，去除冗余                                │
│      └── 压缩后仍超预算 → Level 2                             │
│                                                             │
│  Level 2: 时间压缩                                           │
│  ├── 合并 30 天以上未访问的相似记忆                             │
│  ├── 使用 9 段摘要模板生成摘要                                 │
│  └── 压缩后仍超预算 → Level 3                                 │
│                                                             │
│  Level 3: 自动压缩                                           │
│  ├── 按重要性排序所有记忆                                      │
│  ├── 低优先级记忆压缩为摘要                                    │
│  ├── 保留高优先级记忆原文                                      │
│  └── 压缩后仍超预算 → Level 4                                 │
│                                                             │
│  Level 4: 响应式压缩（紧急）                                   │
│  ├── 只保留最关键的 3-5 条记忆                                  │
│  ├── 生成极简摘要（1 段）                                     │
│  └── 记录压缩日志，下次优先恢复                                │
└─────────────────────────────────────────────────────────────┘
```

### 6.3.5 钩子执行管道

**事件触发→匹配→执行→结果处理**：

```
┌─────────────────────────────────────────────────────────────┐
│                    钩子执行管道                                │
│                                                             │
│  Step 1: 事件触发                                            │
│  ├── 系统事件（sessionStart、contentSave 等）                  │
│  ├── AI 事件（preAIChat、postToolUse 等）                     │
│  └── 用户事件（branchCreate、characterUpdate 等）              │
│                                                             │
│  Step 2: 钩子匹配                                            │
│  ├── 遍历已注册的钩子                                         │
│  ├── 匹配事件名称                                             │
│  ├── 匹配正则条件（如有）                                      │
│  └── 检查启用状态                                             │
│                                                             │
│  Step 3: 钩子排序                                            │
│  ├── 按优先级排序（高→低）                                     │
│  ├── deny 类型钩子优先执行                                     │
│  └── 同优先级按注册顺序                                        │
│                                                             │
│  Step 4: 钩子执行                                            │
│  ├── 串行执行每个匹配的钩子                                    │
│  ├── 每个钩子有独立超时（默认 5 秒）                            │
│  ├── 收集每个钩子的返回结果                                    │
│  └── 遇到 deny 立即停止后续执行                                │
│                                                             │
│  Step 5: 结果处理                                            │
│  ├── 合并所有 modify 结果                                     │
│  ├── 收集所有 inform 日志                                     │
│  ├── 如有 deny，阻止操作并通知用户                              │
│  └── 记录审计日志                                             │
└─────────────────────────────────────────────────────────────┘
```
