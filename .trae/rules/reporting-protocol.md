## 一、汇报总则

### 1.1 核心原则

**Trae 不只写代码，还必须输出任务计划、执行过程、测试结果、集成结果、风险和下一步。**

每次任务必须遵守固定循环：

```
任务理解 → 实施计划 → 开发进度 → 测试结果 → 集成结果 → 风险与阻塞 → 下一步计划
```

### 1.2 汇报类型与目的

| 汇报类型 | 触发时机 | 目的 |
|----------|----------|------|
| 任务理解 | 动代码前 | 确认没有误解目标，防止越界 |
| 阶段进度 | 每完成一个 STDD 阶段 | 跟踪进展，发现偏离 |
| 测试结果 | 跑完测试后 | 判断功能是否真的可用 |
| 集成结果 | UI+Provider+Hook+Mock 跑通后 | 验证分层是否正确 |
| 最终交付 | 任务结束后 | 完整归档，为下一轮做准备 |
| Tabbit 摘要 | 最终交付后附赠 | 供主控快速审查 |

### 1.3 禁止行为

- 不允许无计划直接改代码
- 不允许只说"已完成"
- 不允许省略测试命令
- 不允许从 repo root 运行 `bun test`
- 不允许越界修改 OpenCode 底座
- 不允许 UI 直接修改 mock-data
- 不允许新增依赖而不说明原因
- 如果测试未执行，必须说明原因
- 如果遇到阻塞，必须先汇报，不要绕过规则

## 二、汇报等级

按任务大小分三级，避免所有任务都写长报告。

| 等级 | 适用情况 | 汇报要求 |
|------|----------|----------|
| **L1 小改动** | 文案、样式、小 bug | 简短说明 + 修改文件 + 验证结果 |
| **L2 功能切片** | 新增 Hook、Provider、组件交互 | 计划 + 文件清单 + 测试 + 集成结果 |
| **L3 架构/边界改动** | 项目规则、数据流重构、真实 Agent 接入 | STDD Spec + 分阶段计划 + 风险评估 + 完整验证 |

**判定标准**：
- 小说编辑器 / Mock Provider / AI 任务流 / 3D 镜头编辑器 → 至少 L2
- 涉及 `packages/opencode` / `packages/sdk` / 根目录配置 / 构建脚本 → 必须 L3

## 三、任务开始前：任务理解汇报

**触发条件**: 收到任务后，动代码之前。

```text
## 任务理解汇报

任务名称：
[一句话说明本次任务]

目标：
[本次要完成什么用户可见或技术可验证结果]

不做范围：
[明确本次不做什么，避免扩散]

所属区域：
- [ ] OpenCode 底座
- [ ] packages/app 业务扩展
- [ ] novel 小说编辑器
- [ ] novel-canvas 故事画布
- [ ] novel-3d 3D 镜头
- [ ] 配置/文档/规则

预计修改文件：
1. [文件路径] - [修改原因]
2. [文件路径] - [修改原因]

是否触及保护区域：
- [ ] 否
- [ ] 是，涉及：[列出目录/文件]
如果是，说明为什么业务层无法解决：

STDD Spec：
1. 用户目标：
2. 输入：
3. 输出：
4. 状态变化：
5. 成功路径：
6. 失败路径：
7. 验收标准：

Mock 策略：
[说明是否需要 mock-data / Mock Provider / Fake Agent / mock-delay]

验证计划：
1. [命令]
2. [命令]
3. [手动验证步骤]
```

**作用**: 防止 Trae 一开始就乱改。必须先说清楚准备改哪里、为什么改、怎么验收。

**等待确认后才可开始改代码。**

## 四、执行中：阶段进度汇报

**触发条件**: 任务超过一个步骤时，每完成一个 STDD 阶段。

**强制汇报节点**:

```
1. 写完 Spec 后
2. 改完 types 后
3. 改完 Provider/Mock 后
4. 改完 Hook 后
5. 改完 UI 后
6. 跑完测试后
7. 集成验证后
```

```text
## 阶段进度汇报

当前阶段：
[例如：Types 已完成 / Provider 已完成 / UI 接入中]

已完成：
1. [完成项]
2. [完成项]

正在处理：
1. [当前动作]

发现的问题：
1. [问题]
2. [问题]

是否偏离原计划：
- [ ] 否
- [ ] 是，原因：[说明]

新增或变更文件：
1. [文件路径] - [状态：新增/修改/删除]

下一步：
[下一步具体动作]
```

## 五、测试后：测试结果汇报

**触发条件**: 执行完测试命令后。

**关键要求**: 不能只写"测试通过"，必须写命令、范围、结果、失败原因。

```text
## 测试结果汇报

测试环境：
- 当前目录：
- Node/Bun：
- Package：
- 分支/提交：

执行命令：
```bash
[实际执行的命令，必须是 packages/app 内的命令，不是 root]
```

结果：
- [ ] 通过
- [ ] 失败
- [ ] 部分通过
- [ ] 未执行

输出摘要：
```text
[粘贴关键输出，不要粘贴超长日志]
```

覆盖范围：
1. [测试了什么]
2. [测试了什么]

失败详情：
1. 错误信息：
2. 可能原因：
3. 已尝试修复：
4. 是否阻塞本任务：

未执行测试：
1. [测试项] - 原因：[为什么没执行]
```

**特别强调**: 不要从 root 跑 `bun test`。正确格式：

```bash
cd packages/app && bun typecheck
cd packages/app && bun test
cd packages/app && bun build
```

根据任务不同选择对应命令。

## 六、集成后：集成结果汇报

**触发条件**: UI + Provider + Hook + Mock 全部接入后。

**核心目的**: "测试通过"不等于"集成成功"。尤其小说编辑器这类多层功能需要单独汇报。

```text
## 集成结果汇报

集成范围：
1. Types：
2. Mock Data：
3. Provider：
4. Hook：
5. UI Component：
6. Route/Page：
7. Test：

数据流验证：
[例如：ChapterEditor -> useNovelChapters -> NovelChapterProvider -> mock-data copy -> UI refresh]

用户操作验证：
1. [操作步骤]
2. 预期结果：
3. 实际结果：

Mock 验证：
- [ ] 成功路径
- [ ] 失败路径
- [ ] 空数据
- [ ] 权限/额度/取消等 AI 状态
- [ ] 不适用

是否仍有 UI 直接访问 mock-data：
- [ ] 否
- [ ] 是，位置：[文件路径:行号]

是否触及 OpenCode 底座：
- [ ] 否
- [ ] 是，位置：[文件路径]

集成结论：
[可集成 / 暂不可集成 / 需要下一轮修复]
```

**此模板专门用于审查小说编辑器开发是否遵守"UI 不直接依赖 Mock 数据"的原则。**

## 十、硬性规则

以下规则违反任何一条即视为违规：

| # | 规则 | 违规后果 |
|---|------|----------|
| 1 | 不允许无计划直接改代码 | 需退回重做 |
| 2 | 不允许只说"已完成" | 需补充完整报告 |
| 3 | 不允许省略测试命令 | 需补充执行并汇报 |
| 4 | 不允许从 repo root 运行 bun test | 需进入正确 package 重跑 |
| 5 | 不允许越界修改 OpenCode 底座 | 需回滚并说明 |
| 6 | 不允许 UI 直接修改 mock-data | 需重构为 Provider/Hook |
| 7 | 不允许新增依赖而不说明原因 | 需评估替代方案 |
| 8 | 测试未执行必须说明原因 | 补充原因或补测 |
| 9 | 遇到阻塞必须先汇报 | 禁止绕过规则 |

## 十一、协作节奏

### 推荐日常流程

```
用户给 Trae：一个小任务 + 汇报协议
    ↓
Trae 返回：任务理解汇报（等待确认）
    ↓
用户确认 or 修改
    ↓
Trae 开发：阶段汇报（每完成一个 STDD 层）
    ↓
Trae 完成：最终交付汇报 + Tabbit 摘要
    ↓
用户把 Tabbit 摘要贴给主控
    ↓
主控审查：边界、风险、下一步
    ↓
用户将主控意见反馈给 Trae
```

### 角色分工

| 角色 | 职责 |
|------|------|
| **Tabbit（主控）** | 规则制定、审查、任务拆分、风险判断 |
| **Trae（执行代理）** | 本地代码执行、测试、集成、结果汇报 |
| **User（你）** | 确认方向、转交摘要、决定下一步 |

### 最短版启动命令

如果想简化，每个任务开头固定加这句即可：

> **本任务必须按 STDD + Mock Provider 原则执行。开始前先输出任务理解、Spec、预计修改文件和验证计划；执行中按阶段汇报；完成后输出修改文件、测试命令与结果、集成结果、风险、下一步，并额外给出"给 Tabbit 审查用摘要"。未经确认不要开始改代码。**
