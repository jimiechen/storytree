### **这个 Bug 的根因不是 Three.js，而是 Solid.js 的细粒度反应式系统把 `entries` 这个“闭包内可变数组”视为非反应式数据，被 effect 多次重入或读取时机错位导致看似为空；正确修复方向是 Signal 包装 entries + 拆分 effect + TransformControls 在 attach 前从场景图实时查找 mesh，而不是依赖 `cylManager.entries` 这个外部裸引用。**

---

## **一、核心结论：这是 Solid + Three.js 集成模式问题，不是 Three.js Bug**

报告里最关键的一条线索其实已经揭示了答案：

```text
[CylinderManager] update done, entries: ['cyl-xxx']     ← update 内部 entries 有值
[ThreeViewport] cylManager.entries: []                  ← effect 中读取时 entries 为空
```

**同一次同步 JavaScript 执行流，里外读到不同结果**——这在普通 JS 中不可能发生，除非中间发生了：

```text
1. 该 effect 被触发了不止一次
2. 第二次触发时 update() 又重新构建了一份 entries
3. 第二次 update() 因为某些条件（比如 selectedObjectId 变化）走了不同分支，把 entries 清空或重置
4. 你看到的"empty []"是第二次执行的结果，而 ['cyl-xxx'] 是第一次
```

也就是说，并不是“同一次 effect 内 entries 莫名其妙被清空”，而是 effect 被 Solid 的细粒度依赖追踪触发了 **多次**，你看到的两条日志其实属于 **两次不同的 effect 执行**，被你误以为发生在同一次。

让我把怀疑路径展开。

---

## **二、最可能的根因：`createEffect` 在同一 batch 内触发两次，第二次清空了 entries**

回顾你的 store：

```ts
const selectCylinder = (id: string | undefined) => {
  setScene(prev => ({
    ...prev,
    selectedObjectId: id,
    cylinders: prev.cylinders.map(c => ({ ...c, selected: c.id === id }))
  }));
};
```

这里同时改了两件事：

```text
selectedObjectId
cylinders（每个对象的 selected 字段）
```

而 ThreeViewport 的 effect 同时依赖 `props.store.scene()`，所以每次 `setScene` 都会让整个 effect 重跑。

但更关键的是 `cylinder-manager.update()` 的内部行为。从代码片段看：

```ts
let entries: CylinderMeshEntry[] = [];

const update = (cylinders, selectedId) => {
  // 大概率会做 diff:
  // - 删除不在 cylinders 中的旧 mesh
  // - 创建新 mesh
  // - 更新 selected 状态
  // 然后重新构建 entries
};
```

如果 `update()` 内部的“diff & rebuild entries”逻辑里，存在以下任一情况，就会出现“entries 看似被清空”的现象：

```text
1. 先 entries = []，再 push() — 中间任意 await/微任务断点都会读到空
2. 在 selectedObjectId 变化分支里走了 dispose 路径，错误地把 entries 清掉
3. update 被并发调用两次，第二次的 entries.length=0 状态覆盖了第一次
4. entries 是从 group.children 重建的，但 group.children 因为某次 remove 短暂为空
```

加上 Solid 的 `setScene(prev => ({ ... cylinders: prev.cylinders.map(...) }))` 创建了一个 **全新的 cylinders 数组引用**，diff 算法可能误认为“所有旧 cylinder 都消失了，所有新 cylinder 都是新增”，从而走了 dispose-and-recreate 路径。

简单说：

```text
点击选中
  ↓
setScene 创建全新 cylinders 数组
  ↓
update() 看到新数组引用，认为旧 entries 全部失效
  ↓
dispose 旧 mesh + entries.length = 0
  ↓
重新创建 mesh，但创建过程中或之后又被另一个 effect 重入打断
  ↓
你最终读到的 entries 是中间态：[]
```

---

## **三、第二个根因：`cylManager.entries` 是一个非反应式的外部引用，Solid 不可能在它变化时重跑 effect**

这是 Solid.js 集成命令式库（Three.js、Pixi、CodeMirror、Monaco）的经典坑。

`createEffect` 的依赖追踪只追踪：

```text
1. signal getter 的调用
2. store proxy 的属性读取
```

而你这里：

```ts
console.log('[ThreeViewport] cylManager.entries:', cylManager.entries.map(...));
const entry = cylManager.entries.find(...);
```

`cylManager.entries` 是一个普通对象属性，**Solid 完全不知道它是反应式的**。所以即使 `update()` 内部把 entries 改对了，effect 也不会因为 entries 变化重跑——它只会因为 `props.store.scene()` 变化重跑。

这就解释了为什么你看到 entries 内部 push 成功，但 effect 拿到空：因为 effect 触发的时机和 entries 真正“写入完成”的时机并不绑定。

---

## **四、第三个根因：TransformControls 不应该绑定到 `entries` 里的 mesh，应该实时从 group 中查找**

即使前面两个问题都解决，你的设计也是脆弱的：

```text
TransformControls.attach(entry.mesh)
```

依赖 entries 里的 mesh 引用，而 mesh 一旦在某次 update 中被 dispose-recreate，旧引用就失效了。TransformControls 拿着旧的 mesh 引用，要么报错，要么绑到一个已经从场景中移除的对象上。

**正确做法**：选中状态下，TransformControls 永远从 `cylManager.group.children` 实时查找 `userData.id === selectedId` 的 mesh，而不是缓存引用。

### **步骤 1：把 entries 改成 Signal，让它进入 Solid 的反应式系统**

`cylinder-manager.ts` 改造：

```ts
// novel-3d/components/ThreeViewport/cylinder-manager.ts
import * as THREE from 'three';
import { createSignal, type Accessor } from 'solid-js';

export interface CylinderMeshEntry {
  id: string;
  mesh: THREE.Mesh;
}

export interface CylinderManager {
  group: THREE.Group;
  entries: Accessor<CylinderMeshEntry[]>;        // ← 改为 Accessor
  update: (cylinders: CylinderState[], selectedId?: string) => void;
  dispose: () => void;
  raycast: (raycaster: THREE.Raycaster) => CylinderMeshEntry | null;
  findById: (id: string) => CylinderMeshEntry | undefined;  // ← 新增便捷方法
}

export function createCylinderManager(): CylinderManager {
  const group = new THREE.Group();
  group.name = 'CylinderGroup';

  const [entries, setEntries] = createSignal<CylinderMeshEntry[]>([]);
  const meshMap = new Map<string, THREE.Mesh>();   // ← 用 Map 做 diff，避免误删

  const update = (cylinders: CylinderState[], selectedId?: string): void => {
    const incomingIds = new Set(cylinders.map(c => c.id));

    // 1. 删除已不存在的 mesh
    for (const [id, mesh] of meshMap) {
      if (!incomingIds.has(id)) {
        group.remove(mesh);
        mesh.geometry.dispose();
        (mesh.material as THREE.Material).dispose();
        meshMap.delete(id);
      }
    }

    // 2. 新增或更新 mesh
    for (const c of cylinders) {
      let mesh = meshMap.get(c.id);
      if (!mesh) {
        const geom = new THREE.CylinderGeometry(c.radius, c.radius, c.height, 32);
        const mat = new THREE.MeshStandardMaterial({
          color: c.color,
          emissive: c.id === selectedId ? 0xffaa00 : 0x000000,
          emissiveIntensity: c.id === selectedId ? 0.4 : 0,
        });
        mesh = new THREE.Mesh(geom, mat);
        mesh.userData.id = c.id;          // ← 关键：永远能从场景反查
        mesh.userData.kind = 'cylinder';
        group.add(mesh);
        meshMap.set(c.id, mesh);
      } else {
        // 仅更新选中高亮
        const mat = mesh.material as THREE.MeshStandardMaterial;
        const isSelected = c.id === selectedId;
        mat.emissive.setHex(isSelected ? 0xffaa00 : 0x000000);
        mat.emissiveIntensity = isSelected ? 0.4 : 0;
      }
      mesh.position.set(c.position.x, c.position.y, c.position.z);
      mesh.scale.set(c.scale ?? 1, c.scale ?? 1, c.scale ?? 1);
    }

    // 3. 一次性提交 entries
    const next: CylinderMeshEntry[] = [];
    for (const c of cylinders) {
      const m = meshMap.get(c.id);
      if (m) next.push({ id: c.id, mesh: m });
    }
    setEntries(next);
  };

  const findById = (id: string) => entries().find(e => e.id === id);

  const raycast = (raycaster: THREE.Raycaster) => {
    const hits = raycaster.intersectObjects(group.children, false);
    if (hits.length === 0) return null;
    const hit = hits[0].object;
    const id = hit.userData?.id;
    if (!id) return null;
    return { id, mesh: hit as THREE.Mesh };
  };

  const dispose = () => {
    for (const [, mesh] of meshMap) {
      mesh.geometry.dispose();
      (mesh.material as THREE.Material).dispose();
    }
    meshMap.clear();
    setEntries([]);
    group.clear();
  };

  return { group, entries, update, dispose, raycast, findById };
}
```

关键变化：

```text
1. entries 变成 Signal，effect 会因 entries 变化自动重跑
2. 用 meshMap 做增量 diff，不再 dispose-recreate
3. mesh.userData.id 永远存在，可从场景图反查
4. update() 内部一次性 setEntries，避免中间态被读到
```

### **步骤 2：拆分 ThreeViewport 中的 effect，让 TransformControls 绑定独立反应**

`ThreeViewport.tsx` 改造：

```tsx
// novel-3d/components/ThreeViewport/ThreeViewport.tsx
import { createEffect, onCleanup, on } from 'solid-js';

// ...

// Effect 1: 同步 cylinder mesh 数据（只关心 cylinders 数组本身）
createEffect(on(
  () => props.store.scene().cylinders,
  (cylinders) => {
    const selectedId = props.store.scene().selectedObjectId;
    cylManager.update(cylinders, selectedId);
  }
));

// Effect 2: 同步 selected 高亮（只关心 selectedObjectId）
createEffect(on(
  () => props.store.scene().selectedObjectId,
  (selectedId) => {
    // 仅更新高亮，不重建 mesh
    const cylinders = props.store.scene().cylinders;
    cylManager.update(cylinders, selectedId);
  }
));

// Effect 3: TransformControls 绑定（依赖 entries Signal + selectedId）
createEffect(() => {
  const selectedId = props.store.scene().selectedObjectId;
  const list = cylManager.entries();    // ← 触发 Solid 依赖追踪

  if (!selectedId) {
    transformControls.detach();
    console.log('[TransformControls] detached: no selection');
    return;
  }

  const entry = list.find(e => e.id === selectedId);
  if (!entry) {
    // 容错：从场景图实时反查（防止 entries 还没同步）
    const fallback = cylManager.group.children.find(
      o => o.userData?.id === selectedId
    ) as THREE.Mesh | undefined;
    if (fallback) {
      transformControls.attach(fallback);
      console.log('[TransformControls] attached via scene fallback:', selectedId);
    } else {
      transformControls.detach();
      console.warn('[TransformControls] selected id not found anywhere:', selectedId);
    }
    return;
  }

  transformControls.attach(entry.mesh);
  console.log('[TransformControls] attached:', selectedId);
});

onCleanup(() => {
  transformControls.detach();
  cylManager.dispose();
});
```

要点：

```text
1. 用 on() 显式声明依赖，避免一个 effect 同时依赖多个变量被重复触发
2. effect 1 和 effect 2 都调 update()，是 OK 的，因为 update() 内部用 Map diff，幂等
3. effect 3 依赖 entries() 这个 Signal，当 update() 完成 setEntries 后会自动重跑
4. 加 fallback：从 group.children 用 userData.id 反查，作为最后兜底
```

### **步骤 3：确保 TransformControls 被加入场景，并和 OrbitControls 互斥**

报告里提到“gizmo 根本没出现”，除了绑定问题，还要确认：

```ts

  orbitControls.enabled = !event.value;
});

// 拖拽结束后回写 store
transformControls.addEventListener('objectChange', () => {
  const obj = transformControls.object;
  if (!obj || !obj.userData?.id) return;
  store.updateCylinder(obj.userData.id, {
    position: { x: obj.position.x, y: obj.position.y, z: obj.position.z },
    scale: obj.scale.x,
  });
});
```

## **五、为什么这套方案稳**

第一，它解决了根本问题：**让命令式 Three.js 数据进入 Solid 的反应式图**。entries 变成 Signal 之后，TransformControls 的绑定 effect 会在数据真正更新完成之后才跑，不再依赖时序运气。

第二，**增量 diff** 让 update 不再粗暴 dispose-recreate。即使 selectCylinder 触发整个 cylinders 数组引用换新，已有的 mesh 也不会被销毁，TransformControls 拿到的引用始终有效。

第三，**`userData.id` + 场景反查 fallback** 提供了第二层保护。哪怕未来某次 entries 同步晚了一帧，TransformControls 也能从场景图直接找到对应 mesh，不会出现 detach 又 attach 不上的情况。

第四，**effect 拆分 + on() 显式依赖** 阻断了“一改全跑”的雪崩反应，避免一次 setScene 触发整条管线重跑两三次。

第五，**scene.add(transformControls.getHelper())** 是 Three.js r169+ 之后的硬性要求，0.184.x 一定要这样写，否则 gizmo 永远不显示——这一条本身就可能是“gizmo 不出现”的直接原因，绝不能漏。
