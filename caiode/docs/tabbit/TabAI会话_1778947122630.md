### **这套需求等于把 Git Worktree + Multi-Agent Sandbox + Canvas 协作 三件事叠到小说编辑器里，方向非常有想象力，但必须先把它从 MVP 里隔离出去——本期 MVP 先做单分支单画布的"地基版"，留出 Worktree 接口和 Canvas 数据形态，等 M2/M3 再正式落地多分支沙箱与对比合并。** 直接把这一整套塞进 14 天 MVP 会让你失去最重要的"先跑通文本→场景→镜头"那条主线，得不偿失。下面我把这套新需求重新梳理为一份完整、可执行、可分阶段交付的扩展规划。

---

## **一、先校准这个新需求的真实形态**

你说的这套机制其实是三个独立子系统的组合，不能当成一个功能看：

```text
1. Worktree 沙箱 = 每个分支一份独立的小说工程数据 + 独立的 AI Agent 进程 + 独立的模型/Provider 配置
2. 小说画布（Canvas）= 每个分支里的故事可视化工作面（角色/场景/章节的图谱式呈现，类 Figma/白板）
3. 分支对话与对比合并 = 在 OpenCode chat 里跨分支查询进度、对比章节差异、做"小说分支合并"
```

它的灵感来源很明确：

```text
- Claude Code 里 Fork agents、Worktree 模式（不同子 Agent 跑不同 worktree）
- Git worktree（同仓库多目录、多分支并行）
- AI 写作工具的"多结局/多版本探索"模式
- 白板类工具（FigJam、tldraw）做的故事画布
```

这三件事在 Creative Studio 的语境下都成立，但它们的工程代价**完全不在一个量级**。下面分别评估。

---

## **二、对每个子系统的可行性评估**

### **2.1 Worktree 沙箱（每分支独立模型 + 独立数据）**

**可行性**：✅ 高，是这套需求里最"Claude Code-style"的一块，和你已有的 Agent Runtime 架构天然契合。

**核心抽象**：

```text
NovelWorktree
  ├── id                         分支 id（绑定 Git 分支名 / 内部分支名）
  ├── projectId                  所属项目
  ├── branchName                 分支名（main / draft-A / explore-villain-arc）
  ├── workspacePath              磁盘上独立目录，存放该分支的 .novelproj 工程文件
  ├── agentSession               独立的 Agent Runtime 会话
  ├── providerConfig             独立的 LLM Provider 配置（模型/密钥/温度/上下文窗口）
  ├── status                     idle / writing / generating / merging / archived
  ├── lastActivityAt
  └── lockFile                   防止两个 Agent 同时写一个分支
```

**关键工程点**：

```text
1. 每个分支必须是磁盘上一份独立的工程数据，不能共享 store。
   否则分支切换时撤销栈、自动保存、AI 任务历史都会串。
2. 每个分支必须有独立的 Agent 上下文（不只是 chat 历史，还包括加载的 Skill、注入的 Character/Location 上下文）。
3. Provider 配置必须挂在分支级，不在全局。这是这个需求和"普通项目设置"的根本差异。
4. 必须有 lock 机制，防止多个 chat 实例并发写同一个分支文件。
```

**风险**：分支数量增长后，磁盘空间和 Agent 进程数会线性膨胀。需要有"归档"机制把不活跃分支冷冻。

**结论**：值得做，但不是 MVP，建议落在 **M2 末或 M3 初**。

---

### **2.2 小说画布 Canvas（每分支一份）**

**可行性**：⚠️ 中等，技术不难（Pixi / Konva / tldraw 都行），难在"画什么"。

这一块最容易跑偏。"小说画布"这个概念在不同人脑子里至少有 5 种解读：

```text
A. 故事结构图（章节-场景-镜头的树/网）
B. 角色关系图（角色之间的关系、立场、冲突）
C. 时间线（事件按时间轴排布）
D. 世界观地图（地点之间的空间关系）
E. 自由白板（贴便签、画箭头）
```

**强烈建议第一版 Canvas 只做 A 和 B 两种**，并以"自动布局 + 可拖拽微调"的方式生成，而不是空白白板让用户自己画。原因：

```text
- 空白白板诱使用户花时间装修而不是写作
- 自动布局可以从已有的 Scene / Character 数据派生，零额外维护成本
- 后续 M3 接 Storyboard 时，Canvas 还能多一种"分镜流图"视图
```

**数据结构**：

```text
NovelCanvas
  ├── id
  ├── worktreeId                 必须挂在分支下
  ├── viewMode                   'structure' | 'character' | 'timeline' | 'free'
  ├── nodes[]                    自动派生 + 用户微调位置/标签
  ├── edges[]
  ├── viewport                   缩放/平移状态
  └── lastSyncedFromDataAt       和小说数据上次对齐时间
```

**关键原则**：

```text
Canvas 是数据的"视图"，不是数据本身。
用户在 Canvas 上加节点 = 在小说数据里加 Scene/Character。
Canvas 不存独立的故事内容，永远从 NovelProject 派生。
```

否则会变成"小说一份、Canvas 一份"，永远对不上。

**结论**：值得做，但**第一版只做"结构图视图"**，作为 M2 的内容；自由白板和角色关系图放到 M3-M4。

---

### **2.3 分支对话 + 分支对比 + 分支合并**

**可行性**：分三档。

```text
分支对话（在 chat 里查询某个分支的进度）       ✅ 高
分支对比（看两个分支章节文本差异）             ✅ 高
分支合并（自动合并两个分支的小说内容）         ⚠️ 低，慎做
```

**分支对话**：本质上就是 chat 上下文里加一个 "scope: branchId" 字段，Agent 在回答前只读对应分支的工程数据。技术不难。

**分支对比**：纯文本 diff（章节级 / 场景级），用现成 diff 库（diff-match-patch / jsdiff）。关键不是 diff 算法，而是**呈现方式**。建议三种视图：

```text
- 章节级 diff：左右并列章节文本，红绿高亮
- 场景级 diff：表格对比 Scene 字段（title / summary / goal / conflict 等）
- 镜头级 diff：表格对比 Shot 字段
```

**分支合并**：这件事我必须明确提示风险。代码可以三方合并，因为代码有明确语义和测试；**小说文本不能机械合并**。如果 A 分支把第三章主角改成"被反派抓走"，B 分支把第三章主角改成"主动潜入敌营"，自动合并会产生不可读的乱炖。

正确做法是把"合并"重新定义为：

```text
不要做自动 merge。
做"挑选式 cherry-pick"：以场景/镜头为粒度，让用户从分支 A 选 N 个场景、从分支 B 选 M 个场景，组装成一个新分支。
合并冲突 = "选哪个版本"，而不是"算法解决"。
```

让 AI 来做的是**辅助**：识别冲突点、给出"选 A / 选 B / 由 AI 改写一版折中"三个选项，最终决定权在用户。

**结论**：分支对话和分支对比可以做，分支合并要换个产品定义（"组装新分支"而非"自动合并"），全部建议落在 **M3**。

## **四、数据模型升级（向 Worktree 兼容）**

为了让 MVP 不挖坑，今晚就要把 types.ts 里的顶层结构从"项目 = 一份数据"改成"项目 = 一组分支"，但**MVP 阶段只用一个默认分支**。这样未来加分支不用迁移老存档。

```ts
// packages/novel-core/src/types.ts
export interface NovelProjectMeta {
  schemaVersion: 2;             // 从 1 升到 2，因为引入 worktree 顶层
  id: string;
  title: string;
  createdAt: string;
  updatedAt: string;
  settings: { theme: 'light' | 'dark' };

  defaultWorktreeId: string;    // MVP 阶段固定 'main'
  worktreeIds: string[];        // MVP 阶段只有一个
}

export interface NovelWorktree {
  id: string;
  branchName: string;
  parentBranchId?: string;       // 从哪个分支 fork 出来
  createdAt: string;
  updatedAt: string;
  status: 'active' | 'archived';

  providerConfig?: {             // M2 启用，MVP 阶段为空
    providerId: string;
    model: string;
    temperature?: number;
    maxTokens?: number;
  };

  // 实际故事数据
  chapters: Chapter[];
  scenes: Scene[];
  shots: Shot[];
  characters: Character[];
  locations: Location[];

  // Canvas 视图状态（M2 启用）
  canvas?: NovelCanvas;

  // Agent 会话（M2 启用）
  agentSessionId?: string;
}

export interface NovelCanvas {
  viewMode: 'structure' | 'character' | 'timeline';
  viewport: { x: number; y: number; zoom: number };
  nodeOverrides: Record<string, { x: number; y: number; pinned?: boolean }>;
  // 节点和边都从故事数据派生，这里只存"用户的视图覆盖"
}
```

**磁盘结构**（M2 起）：

```text
my-novel.novelproj/
├── project.json                # NovelProjectMeta
├── worktrees/
│   ├── main/
│   │   ├── worktree.json       # NovelWorktree（含所有故事数据）
│   │   ├── chat-history.jsonl  # Agent 会话历史
│   │   └── canvas.json
│   ├── draft-a/
│   │   ├── worktree.json
│   │   ├── chat-history.jsonl
│   │   └── canvas.json
│   └── explore-villain/
│       └── ...
└── assets/                     # M3 起，资产引用
```

**MVP 阶段**：仍然用单文件 `.novelproj.json`，但内部已经是上面的结构，只是 `worktrees` 数组里只有一个 `main` 分支。M2 切换到目录模式时只是把 JSON 拆成多个文件，零数据迁移。

## **五、Worktree 与 Git 的关系**

你用了 "Worktree" 这个词，需要明确一件事：**这个 Worktree 不需要真正调用 git worktree 命令**。

```text
真正用 git worktree：
  优点：用户的小说目录就是一个 git 仓库，原生版本控制
  缺点：
    - 二进制资产（图像/视频）爆仓库
    - 用户不一定懂 git
    - .novelproj 目录结构和 git 工作目录强耦合，未来云同步麻烦

不用 git worktree（推荐）：
  自己实现"逻辑分支"概念，每个分支是 worktrees/ 下的一个子目录
  自己实现 fork / diff / cherry-pick
  概念上叫 "Worktree" 是借词，向用户传达"独立沙箱"语义
```

**强烈建议不用真正的 git worktree**。我们要的是"沙箱隔离 + 数据独立 + Agent 独立"这套语义，不需要绑死 git。

如果将来用户想要版本控制，可以**额外**提供一键 "导出为 git 仓库" 功能。

## **六、Provider 配置下沉到分支的设计**

你这条需求的精髓在于"每个分支可以指定不同模型"。这件事的工程含义：

```text
Provider 配置必须挂在 Worktree 级，不在 Project 级，更不在 Global 级
当用户在分支 A 跑一个 Skill 时，Agent 必须读 worktreeA.providerConfig 而不是全局
分支切换 = Agent 实例切换 = Provider 实例切换
```

具体实现：

```ts
interface ProviderRegistry {
  getProviderForWorktree(worktreeId: string): TextProvider;
}

// 解析顺序：worktree.providerConfig → project.defaultProvider → global.fallback
```

UI 上：

```text
分支创建对话框最下方有"模型配置"折叠区
默认继承父分支配置
可以点"覆盖"独立指定模型 / 温度 / 上下文窗口大小
分支顶部 Tab 永远显示当前分支用的模型名（小标签）
```

这一块在 MVP 里**只留接口不实现**，M2 才正式启用。但今晚就要把 `worktree.providerConfig` 字段加进 types.ts，避免后期破坏老存档。

## **十、几个最后的产品判断**

第一个判断：**Worktree 沙箱这个想法是对的，而且是你产品的差异化来源。** 现在市面上的 AI 写作工具几乎全是"单线性历史 + 撤销栈"，没人真正做"故事的多版本探索"。如果你能把"用 Mock 模型在分支 A 写一版温情结局，用真实模型在分支 B 写一版黑暗结局"做成一个流畅体验，这就是核心卖点。

第二个判断：**Canvas 不是核心卖点，是"看起来很酷"的辅助。** 用户真正需要的是"我能不能看清自己故事的结构"，而不是"我能不能在白板上画箭头"。所以 Canvas 第一版做"自动从数据派生的结构图"，比做"自由白板"更有价值，也更省力。

第三个判断：**分支合并必须避开"自动 merge"陷阱。** 小说不是代码，没法靠算法合并。把它定义为"组装新分支 + AI 辅助选项"是产品上唯一能跑通的路径。任何"一键合并两份小说"的承诺都会翻车。

第四个判断：**这套机制让 OpenCode chat 框真正变成"故事工作台的指挥中心"。** 用户在 chat 里输入 "把分支 A 的第 3 章和分支 B 的第 5 章对比一下"，Agent 调起对比视图。输入 "在分支 A 基础上 fork 一个新分支 explore-villain，用 Claude Sonnet 跑"，Agent 调起 fork 流程。这就是 Claude-Code-style Agent Runtime 在创作领域真正的样子，比任何"AI 写作助手"都更像生产工具。

---

如果上面这套梳理对得上你脑子里的版本，**今晚就只做 5 件 T0 追加任务，明天仍然按原 MVP 节奏走**。如果你希望把 Worktree / Canvas 也提前进 MVP，需要重新规划 14 天目标——但我必须诚实告诉你：那样做的话，MVP demo 视频出不来的概率会从 20% 涨到 70% 以上。优先级建议是**先把单分支闭环跑通，让人看到能写、能拆、能存**，再用 M2-M3 把这套差异化卖点叠上去。
