### **StoryTree2 重排版作战计划：先 Stitch 出 MVP 静态页 → 再 Mock 装配 + STDD 特征驱动 → 最后逐特性深耕**

你这一次的重排诉求其实把整个项目节奏从"垂直切片"改成了"水平铺面再垂直钻深"——先用 Google Stitch 把 MVP 范围内的所有 UI 页面**一次性生成出来**，再进入一个**专门的 Mock 装配阶段**把这些静态页串成可点击、可路由、可被测试驱动的应用，然后才在 MVP 闭环之上做"特定阶段、特定特征"的深度开发。这个节奏更适合当前 StoryTree2 已经有 `novel/`、`novel-canvas/` 雏形、PRD 已收敛到 21 页的现状，因为它能让"主控可见物"在第 1 周就出现，把风险前置暴露。下面我把整套计划重新排过一遍，并直接给出可喂给 Trae 的指令包。

## **一、节奏重排原则（为什么要分成三段而不是连续 Sprint）**

旧版 5 个 Sprint 的问题在于"每个 Sprint 都同时动 UI、Tool、后端"，对 Trae 这种执行体来说**心智负载过高、回归面太宽**。新版改成**三段式节奏**，每一段只做一类事，错位收敛：

第一段是 **UI-First**——只产出静态页面、不接业务逻辑，全部由 Google Stitch 提示词驱动生成 HTML/JSX，所有"数据"用硬编码假数据。这一段的好处是主控能在 Demo 评审会上直接"翻页式"过完 PRD 21 个页面，把视觉 / 交互 / 文案的争议在写代码前消化掉。第二段是 **Mock & Wire**——把第一段的静态页装到 SolidJS Router 与 Mock Provider 后面，引入 STDD（Specification & Test-Driven Development，规约+测试双驱动）流程，让每一个页面跳转、每一个按钮点击都有 Playwright 红测把守。这一段结束时，整个 MVP 已经"看起来能用"，但所有 LLM 调用、计费、云同步都是 Mock。第三段才是 **Feature Deep-Dive**——按特征（不是按页面）拆深度开发任务，每一个特征都从"把对应页面上的 Mock 拆掉、换成真实实现"开始。

这种分段还有一个隐含好处：**Stitch 生成的页面天然就是 STDD 的"规约"**——页面上写着什么字段、什么按钮，就是规约的一部分，Trae 在第二段写测试时直接从页面 DOM 反推用例，几乎不会偏离 PRD。

## **三、P1 Stitch UI-First 阶段详细规划（这是你本次最关心的部分）**

### **3.1 阶段目标与不变量**

P1 阶段的唯一目标是：**让主控在两周内拿到 21 个可在浏览器里翻看的静态页面**。这一阶段的不变量有三条：① 不允许引入任何业务后端调用，所有数据用 `__mocks__/fixtures/*.json` 提供；② 不允许写任何业务逻辑（连 `onClick` 都不写真函数，只写 `console.log`）；③ 所有页面必须共享同一套设计 token（颜色 / 间距 / 字体 / 圆角），用 CSS Variables 集中管理，方便后续主题化。

### **3.2 21 页 Stitch 提示词的批量生成策略**

PRD 已经在历史会话里给出过 Google Stitch 提示词（30 个页面版），但那一版是面向"独立 mock 平台"的。P1 阶段需要把它**收编进 StoryTree2 仓库**，方法是建立 `docs/stitch/` 目录，把 21 个 PRD 页面对应的 Stitch 提示词拆成 21 个独立 `.md` 文件，命名规则是 `S{编号}-{页面英文名}.md`。每个文件结构固定为五段：**Page Spec（页面定位）→ Layout（栅格布局）→ Components（组件清单含 dataTestId）→ Sample Data（假数据片段）→ Vibe Tone（视觉氛围）**。其中 `dataTestId` 是关键——它直接为 P2 阶段的 Playwright 测试提供选择器锚点，让 Stitch 生成的 HTML 在第二段不用任何修改就能被测试用例选中。

### **3.3 从 Stitch 输出到仓库代码的落地路径**

Stitch 给出的是 HTML+CSS（部分情况是 React JSX），不能直接进 SolidJS 工程，所以 P1 阶段要建立一条**两步转换流水线**：第一步把 Stitch HTML 落到 `caiode/opencode-1.4.0/packages/app/src/novel/__stitch__/{页面名}.html`，作为"原始底片"留档；第二步用一个轻量脚本（`scripts/stitch-to-solid.ts`）把 HTML 自动转换成 SolidJS 组件骨架，输出到 `caiode/opencode-1.4.0/packages/app/src/novel/pages/{页面名}.tsx`。脚本要做的核心工作只有三件：把 `class=` 改成 `class=`（SolidJS 兼容）、把 `data-testid` 原样保留、把 `<script>` 段剥离并丢进单独文件。复杂的交互逻辑一律推迟到 P2，P1 阶段允许页面看起来"按钮按了没反应"。

### **3.4 P1 的退出闸门**

主控在 P1 末尾会做一次"视觉走查会"：21 个页面在桌面 1440px、平板 768px、手机 375px 三档断点下逐页翻看，任何一页存在以下问题不予通过——文案与 PRD 不一致、设计 token 漂移（出现非 token 颜色或非 4 倍数间距）、`dataTestId` 缺失或重名、移动端布局塌陷。通过即"视觉锁版"，进入 P1 之后的 PR 不允许再大改视觉，只能改逻辑。

## **四、P2 Mock 装配 + STDD 阶段详细规划**

### **4.1 STDD 是什么、与 TDD 的差异**

你提到的 STDD（Specification + Test-Driven Development，规约-测试双驱动）在本项目中的具体含义是：**先把页面上的可见规约（按钮文案、字段名、状态机迁移）抽成 Markdown 规约文件，再从规约一对一生成 Playwright 测试用例，最后才写 SolidJS 实现**。这与传统 TDD 的差异在于多了"规约"这一中间层——规约文件 `docs/specs/{页面名}.spec.md` 是主控可读的，测试是机器可读的，两者通过 `dataTestId` 与"规约编号"双向绑定。这套方法的好处是**主控审规约就等于审测试用例**，避免了"测试写出来主控看不懂"的常见死结。

### **4.2 P2 的执行流水线（每页 4 步）**

P2 阶段会以"页"为最小单位推进，每一页都走 4 步：

第一步**抽规约**——Trae 阅读 P1 落地的 `pages/{页面名}.tsx`，把页面上的所有可交互元素与状态变化整理成 `docs/specs/{页面名}.spec.md`，每条规约必须形如 `SPEC-{页面}-{编号}: 当{前置条件}时，{动作}应导致{可观察结果}`。第二步**写红测**——把每条规约一对一翻译成 `tests/e2e/{页面名}.spec.ts` 的 Playwright 用例，每个 `test()` 块的标题必须以 `SPEC-XX` 开头，`bun playwright test` 必须红。第三步**写 Mock 实现**——在 `__mocks__/{页面名}.ts` 中提供假数据与假 Tool 响应，在 `pages/{页面名}.tsx` 中接上 SolidJS Signal 与路由，让红测转绿。第四步**重构**——抽出共享的 Mock 工厂、共享的 Layout 组件、共享的 Signal Store，覆盖率不能降。

整个 P2 阶段下来，仓库里会沉淀出三套互相印证的产物：21 份 `.spec.md` 规约、21 份 `.spec.ts` 测试、21 个 `.tsx` 页面组件，且三者通过 `SPEC-ID` 与 `dataTestId` 形成可追溯链。

### **4.3 Mock Provider 的统一抽象**

为了避免 P3 阶段做特征替换时"每页改一遍"，P2 必须在 `caiode/opencode-1.4.0/packages/shared-schema/src/provider/MockProvider.ts` 定义一个**统一 Mock Provider 接口**，所有页面调用 LLM/计费/同步的入口都走这个接口。它对外暴露的方法签名与未来真实 Provider 完全一致（参数 / 返回 / 流式 chunk 结构），内部用 `setTimeout` + 静态 fixture 模拟。这样 P3 阶段做特征深耕时，**只需把 import 路径从 `MockProvider` 改成 `RealProvider`，零页面代码改动**。这一条是 P2 阶段的核心技术债防御策略，主控会在 PR Review 时盯死。

### **4.4 P2 的退出闸门**

P2 退出标准必须同时满足四点：① `bun playwright test` 全绿且包含全部 SPEC-ID 用例；② 21 个页面之间任意路径可点通，无 404；③ 行覆盖率 ≥ 80%、分支覆盖率 ≥ 70%；④ 跑一次"断网演示"——拔掉网线后整个 Mock MVP 仍可完整走一遍"注册→建项目→生成大纲→生成正文→保存→充值→签到→导出"，没有任何报错。能通过断网演示的 MVP 才算真正"装配完成"。
