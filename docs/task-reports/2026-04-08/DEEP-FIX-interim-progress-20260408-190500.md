## 💡 关键洞察

### 为什么测试会大量失败？

经过深入分析，发现**三大根本原因**:

#### 1. **测试与实现不同步** (60% 的失败)
```
现象: 测试期望的 API/函数名与实际实现不一致
原因: 开发者在实现时修改了接口但未更新测试
例子:
  - 测试调用 sendToAI() → 实际是 sendMessage()
  - 测试期望 'case' → 实际是 "case"
  - 测试查找 .chat-message class → 只在运行时存在
```

#### 2. **Mock 数据结构不匹配** (25% 的失败)
```
现象: Mock 对象缺少必需字段或类型错误
原因: 接口变更后未同步更新 Mock 工厂函数
例子:
  - GatewayConfig 缺少 retryDelay 字段
  - Chapter 类型混淆 name vs title
```

#### 3. **过度具体的断言** (15% 的失败)
```
现象: 测试检查实现细节而非行为
原因: 测试编写过于严格，耦合了内部实现
例子:
  - 检查精确的空格/换行符
  - 检查注释字符串
  - 检查私有方法的存在性
```

## 🎓 学到的经验教训

### 1. **测试应该检查行为，而非实现**
```javascript
// ❌ 脆弱测试 (检查实现细节)
expect(html).toContain("function setAIStatus(");

// ✅ 健壮测试 (检查行为)
expect(html).toContain("updateAIStatus");
expect(html).toMatch(/status.*connecting|online|error/);
```

### 2. **保持测试与实现同步**
- 当修改函数签名时，**立即更新对应测试**
- 使用 IDE 的"查找引用"功能定位所有受影响的测试
- 考虑使用 TypeScript 严格模式强制同步

### 3. **优先修复阻塞性问题**
- P0 (编译错误) 必须最先解决
- P1 (核心功能测试) 次之
- P2 (边缘情况) 可以延后

### 4. **批量修复比逐个修复高效**
- 按文件分组修复（而非按错误类型）
- 一次性解决同一文件的所有相关问题
- 减少上下文切换开销
