## 整体评价

这份计划结构清晰，三阶段递进逻辑合理——先做插件宿主、再重构前端、最后深度集成 OSS Fork，是一条经典的"由外到内"渐进式路径。文档要素齐全（里程碑、测试标准、风险预案、资源需求），具备可执行性。但部分细节存在技术风险被低估、指标设定过于乐观等问题，值得在推进前认真审视。

---

## 第一阶段：caiode 插件宿主

### 亮点

串行化 LLM 请求队列（M1.2）和基于文件路径的 Mutex（M1.3）是解决多 Agent 并发竞争的核心设计，思路正确，优先级排序合理。

### 主要问题

**技术选型存在隐患。** `async-mutex` 仅能保证同一 Node.js 进程内的互斥，而 VS Code Extension Host 与 Python Agent 子进程是跨进程边界的，文件锁必须依赖操作系统级别的文件锁（如 `proper-lockfile` 或 `flock`），否则 M1.3 的设计在多进程场景下根本无效。这是一个需要在 M1.3 开工前明确解决的架构问题。

**质量门禁指标过于模糊。** "高负载下无内存泄漏"缺乏可量化的测试条件定义——10 个 Agent、运行多少分钟、内存增长阈值是多少？建议补充具体的 Heap Snapshot 对比基准。

**风险预案不够完整。** 僵尸进程的 `deactivate` 钩子处理是必要的，但 VS Code 在崩溃（非正常退出）时不会触发 `deactivate`，需要额外考虑守护进程或心跳检测机制作为补充。

---

## 第二阶段：Dreamweaver Webview 重构

### 亮点

将数据层（Prisma + SQLite）下沉至插件宿主、Webview 只负责渲染和交互的分层设计是正确的，符合 VS Code Webview 的最佳实践，也为后续离线化打好了基础。

### 主要问题

**通信性能指标存疑。** "1MB JSON 序列化 + 反序列化 < 50ms"这个目标在低端设备上有一定风险。VS Code 的 `postMessage` 通道会对消息进行结构化克隆（Structured Clone），1MB 数据在主进程和 Webview 渲染进程之间的传输本身就有开销，建议在 M2.2 阶段就建立性能基线测试，而不是等到 M2.4 联调时才发现问题。

**静态导出的兼容性风险被低估。** 风险预案只提到了 SSR 第三方库的问题，但 Next.js `output: 'export'` 的限制远不止于此——`Image Optimization`、`API Routes`、`Middleware`、动态路由等都需要逐一排查。建议在 M2.1 之前先做一次完整的"静态导出可行性扫描"，列出所有需要改造的模块，避免在 M2.2 阶段出现大规模返工。

**缺少 IPC 接口版本管理机制。** 文档提到了"IPC 接口契约文档"，但没有说明当插件与 Webview 版本不一致时的兼容策略。随着迭代推进，这会成为一个持续的维护负担，建议从第二阶段起就引入接口版本号机制。

---

## 第三阶段：VS Code OSS Fork 集成

### 亮点

将前两阶段成果作为 Built-in Extension 打包进 OSS Fork 是正确的最终形态，避免了用户手动安装的摩擦，也便于统一分发和离线部署。

### 主要问题

**这是整个计划中风险最高的阶段，但文档内容却最为单薄。** 第三阶段的技术选型部分仅列出了 Electron、TypeScript 和 Gulp，缺少里程碑分解、测试标准、质量门禁和风险预案，与前两阶段的文档深度严重不对等。Fork VS Code OSS 涉及的工程复杂度极高——多平台构建（Windows/macOS/Linux）、签名与公证、与上游 VSCode 版本的 rebase 策略、Electron 版本锁定等，每一项都可能成为卡点。**强烈建议在第二阶段结束后，专门输出一份第三阶段的详细实施计划，而不是在整体计划中一笔带过。**

**上游同步策略缺失。** Fork 之后如何跟进 VS Code 官方的安全补丁和功能更新？如果长期不同步，会产生严重的技术债。这个问题需要在第三阶段开始前明确决策：是定期 rebase、还是冻结版本、还是只同步安全补丁。

## 跨阶段的共性问题

`dist/` 目录和 `node_modules/` 被纳入版本控制（从之前的 PR diff 可以看到），这是一个需要在正式开发开始前就解决的工程规范问题，否则会持续污染所有 PR 的 diff，影响代码审查效率。
