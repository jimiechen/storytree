# 架构决策：Trae IDE 三种协作模式选择

---

## 三种模式的可行性评估

---

### 模式一：纯 Skill 封装

将三个角色（插件架构师、前端自动化工程师、集成测试工程师）各自封装为独立的 Trae Skill，每个 Skill 内置该角色的专业知识、验证脚本模板和交付物格式。

这种模式的核心优势在于**复用性极强**。一旦"前端自动化工程师 Skill"封装完成，它不仅服务于当前的 CDP PoC 验证，未来任何涉及 React 组件自动化操作的任务都可以直接调用，无需重新描述角色背景。Skill 的调用是显式的、可组合的，适合任务边界清晰的场景。

但纯 Skill 模式的局限也很明显：Skill 本身是无状态的，无法在多个 Step 之间传递上下文（例如 Step 2 产出的 fiber key 名称需要在 Step 3 中使用），每次调用都需要手动将上一步的结果作为输入喂给下一个 Skill。对于 7 步串行依赖的 PoC 验证场景，这会造成大量的手动上下文拼接，实际操作效率并不高。

---

### 模式二：纯智能体（Agent）提示词

为整个 PoC 验证流程创建一个统一的 Trae 智能体，提示词中内置所有三个角色的职责描述、7 个步骤的执行逻辑以及各步骤的验证标准。

这种模式的优势是**上下文连续性最好**。智能体在单次会话中可以自然地从 Step 1 推进到 Step 7，中间产出的数据（selector 路径、fiber key、注入函数）会自动保留在上下文中，无需人工传递。对于强依赖中间状态的任务链，单智能体模式的执行流畅度明显优于多 Skill 拼接。

但纯智能体提示词的问题在于**专业深度受限**。一个提示词试图同时覆盖 CDP 底层连接管理、React Fiber 内部机制、集成测试可观测性设计三个完全不同的专业领域，必然导致每个领域的专业指令被稀释。当遇到 Step 3 这类需要深度攻关的技术难点时，单一智能体往往会给出泛化的通用答案，而不是针对 React 受控组件的精确解法。

---

### 模式三：Rule + Skill + 智能体三者结合

这是最值得重点评估的模式。具体的组合方式是：用 **Rule** 定义跨角色的工作规范和质量门禁，用 **Skill** 封装每个角色的专业能力库，用 **智能体** 负责任务调度和上下文管理。

Rule 层应该定义的是不变的约束，例如"所有 CDP 操作必须经过 CDPSessionManager 接口"、"Step 3 未通过前禁止推进 Step 4"、"每步必须输出结构化验证报告"。这些规则一旦写入 Rule 文件，所有 Skill 和智能体调用都会自动遵守，不需要在每个提示词中重复声明。

Skill 层封装的是可复用的专业原子能力，例如"React Fiber 探查"Skill 内置了 `__reactFiber` 的查询脚本和 fiber key 命名规律的知识，"CDP Session 管理"Skill 内置了连接生命周期管理的最佳实践。这些 Skill 不绑定具体任务，可以在多个项目中复用。

智能体层则专注于任务编排，它知道 7 个步骤的执行顺序、依赖关系和阻塞条件，但不需要自己掌握每个步骤的技术细节，而是在需要时调用对应的 Skill。这种分层设计让智能体的提示词保持简洁，专注于"做什么"而不是"怎么做"。

---

### 三种模式的综合对比

| 维度 | 纯 Skill | 纯智能体 | Rule + Skill + 智能体 |
|------|----------|----------|----------------------|
| 上下文连续性 | 弱（需手动传递） | 强 | 强（智能体负责维持） |
| 专业深度 | 强（各 Skill 专注） | 弱（被稀释） | 强（Skill 保证深度） |
| 可复用性 | 高 | 低（提示词绑定任务） | 最高（Skill 跨项目复用） |
| 质量一致性 | 依赖人工 | 依赖提示词质量 | 高（Rule 强制约束） |
| 初始建设成本 | 中 | 低 | 高 |
| 适合场景 | 单步专业任务 | 短流程连续任务 | 多角色长流程任务 |

---

## 结论与建议

对于当前 PoC 验证这个具体场景，**推荐采用模式三，但分两个阶段落地**。

第一阶段先用单智能体快速跑通整个 7 步验证流程，目的是收集真实的执行数据——哪些步骤容易出错、哪些步骤需要深度专业知识、哪些中间产出需要被后续步骤引用。这个阶段的产出不只是验证结果，更重要的是识别出哪些能力值得被提炼为 Skill。

第二阶段基于第一阶段的经验，将 Step 1/2/3 中反复用到的 CDP 连接逻辑和 React Fiber 探查逻辑封装为独立 Skill，将质量门禁（阻塞项判断、验收标准）写入 Rule 文件，再将智能体提示词精简为纯任务编排逻辑。这样形成的三层体系不仅服务于当前 PoC，也为后续正式开发阶段的多角色协作奠定了可复用的基础设施。

跳过第一阶段直接建设三层体系的风险在于，在没有实际执行数据的情况下设计 Skill 边界，往往会导致 Skill 粒度过粗或过细，后期维护成本反而更高。
