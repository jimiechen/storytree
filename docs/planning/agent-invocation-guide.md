## 一、调用原则总览

智能体的调用遵循**最小权限原则**和**单一职责原则**：
每次任务只激活与当前工作内容匹配的智能体，
避免多智能体同时操作同一模块造成冲突。

所有智能体调用必须在**当前分支处于干净状态**（`git status` 无未提交变更）
后才能启动，否则需先 commit 或 stash 当前工作。

## 二、各智能体调用时机

---

### **智能体 1：VS Code 插件架构师**

#### 何时调用

| 触发场景 | 具体条件 |
|---------|---------|
| **里程碑启动** | 每个 M1.x 里程碑正式开工前，由架构师完成模块设计评审 |
| **核心模块开发** | 需要实现 `ProcessGuardian`、`FileMutex`、`GlobalModelRequestQueue` 任一模块时 |
| **架构决策** | 出现跨模块接口设计争议，或需要输出 ADR（架构决策记录）时 |
| **IPC 协议变更** | 任何涉及 `ipc-protocol.ts` 的接口新增、修改、废弃操作前 |
| **打包配置** | `.vsix` 打包流程调整、`.vscodeignore` 更新、`esbuild.config.mjs` 修改时 |
| **Code Review** | 其他工程师提交涉及核心模块的 PR，需要架构师进行技术评审时 |

#### 不应调用的场景

- 纯文档更新（交给文档智能体处理）
- 前端 Webview 样式调整（交给前端工程师）
- CI/CD 流水线配置（交给 DevOps 工程师）

#### 调用前置条件

```
✅ 当前分支为 feat/DEV-1.x.x-* 格式
✅ 已完成上一里程碑的 Exit Criteria 验收
✅ 相关 Issue 已创建并分配
```

### **智能体 2：Node.js 后端工程师**

#### 何时调用

| 触发场景 | 具体条件 |
|---------|---------|
| **数据层开发** | 需要实现或修改 SQLite 数据库适配层（`sqlite-db.ts`）时 |
| **RPC 层开发** | 实现 HTTP/IPC 双模式 RPC 适配器，或环境切换逻辑调整时 |
| **安全模块** | 实现密钥管理（`secret-manager.ts`）或加密数据库（`encrypted-db.ts`）时 |
| **数据同步** | 云端数据同步推送服务（`sync-push-service.ts`）的开发与调试时 |
| **跨进程协作** | 需要与 Python 工程师联调跨进程文件锁时（Node.js 侧） |
| **性能问题** | 数据库查询慢、RPC 超时等后端性能问题排查时 |

#### 不应调用的场景

- VS Code 插件生命周期管理（交给插件架构师）
- 前端页面逻辑（交给前端工程师）
- Python Agent 内部逻辑（交给 Python 工程师）

#### 调用前置条件

```
✅ VS Code 插件架构师已完成 IPC 接口协议定义
✅ SQLite 数据库 Schema 设计已评审通过
✅ 相关 ADR 文档已存档
```

### **智能体 3：高级前端工程师（React / Next.js）**

#### 何时调用

| 触发场景 | 具体条件 |
|---------|---------|
| **Phase 2 启动** | 第二阶段正式开工，开始 Dreamweaver Webview 重构时 |
| **静态导出扫描** | M2.1 开工前，执行 Next.js 静态导出可行性扫描时 |
| **RPC Client 重构** | 重构 `dreamweaver/src/lib/rpc/` 网络层，实现双模式切换时 |
| **业务模块改造** | 角色库、大纲视图、工作台等模块的 Webview 兼容性改造时 |
| **性能基线测试** | M2.2 阶段建立 `postMessage` 通信性能基线时 |
| **UI 自动化测试** | 编写或维护 Playwright UI 测试套件时 |

#### 不应调用的场景

- Phase 1 阶段（前端工程师在 Phase 1 无工作内容）
- 插件宿主逻辑（交给插件架构师）
- 数据库操作（交给 Node.js 工程师）

#### 调用前置条件

```
✅ Phase 1 所有 Exit Criteria 已通过验收
✅ IPC 接口契约文档（含版本号）已输出
✅ caiode 插件 .vsix 已可离线安装验证
```

### **智能体 4：Python 后端工程师 / AI Agent 集成工程师**

#### 何时调用

| 触发场景 | 具体条件 |
|---------|---------|
| **跨进程锁联调** | DEV-1.3.1 PoC 验证阶段，需要编写 Python 侧文件锁脚本时 |
| **心跳协议实现** | 实现 Python Agent 响应 ProcessGuardian 心跳 ping 的逻辑时 |
| **LLM 队列对接** | Python Agent 需要通过 caiode 队列代理 LLM 调用时 |
| **集成测试脚本** | 编写 `tests/integration/cross-process-lock/` 跨进程测试脚本时 |
| **Agent 任务编排** | 设计或调整 Python Agent 的任务执行与结果回传流程时 |
| **竞态问题排查** | 跨进程并发场景出现数据损坏或死锁时 |

#### 不应调用的场景

- Node.js 侧的文件锁实现（交给插件架构师）
- 前端 Webview 逻辑（交给前端工程师）
- CI/CD 配置（交给 DevOps 工程师）

#### 调用前置条件

```
✅ DEV-1.3.1 文件锁方案选型报告已输出
✅ Node.js 侧 FileMutex 接口已定义
✅ IPC 心跳协议格式已与插件架构师确认
```

### **智能体 5：DevOps / 构建工程师**

#### 何时调用

| 触发场景 | 具体条件 |
|---------|---------|
| **CI 初始化** | M1.0 阶段，首次建立 GitHub Actions 流水线时 |
| **CI 失败修复** | CI 出现持续性失败（非代码问题，而是流水线配置问题）时 |
| **发布流程** | 每次版本发布前，配置或执行 `release.yml` 流水线时 |
| **构建优化** | CI 耗时超过目标值（10 分钟），需要优化构建配置时 |
| **多平台构建** | Phase 3 开始，搭建 VS Code OSS Fork 多平台构建流水线时 |
| **依赖安全扫描** | 定期或发布前执行依赖漏洞扫描时 |
| **上游同步** | VS Code OSS 官方发布安全补丁，需要评估是否同步时 |

#### 不应调用的场景

- 业务代码开发（交给对应业务工程师）
- 测试用例编写（交给 QA 工程师）
- 架构设计决策（交给插件架构师）

#### 调用前置条件

```
✅ 项目仓库已初始化，分支保护规则已配置
✅ GitHub Repository Secrets 已配置（API Key 等）
✅ 需要发布时：所有 Exit Criteria 已通过 QA 验收
```

### **智能体 6：QA 测试工程师**

#### 何时调用

| 触发场景 | 具体条件 |
|---------|---------|
| **里程碑验收** | 每个 M1.x 里程碑完成后，执行对应 TEST 任务时 |
| **Exit Criteria 采集** | 阶段门禁检查前，采集所有实测值并填写报告时 |
| **压测执行** | DEV-1.2.1 完成后，执行 10 Agent × 10 分钟压测时 |
| **跨平台验证** | 跨进程文件锁需要在 macOS / Linux / Windows 三平台验证时 |
| **回归测试** | 每次 PR 合并至 `develop` 后，触发回归测试套件时 |
| **缺陷复现** | 生产或测试环境出现 Bug，需要稳定复现步骤时 |
| **验收报告提交** | 每个里程碑结束，需要提交 `phase1-verification-report.md` 时 |

#### 不应调用的场景

- 功能代码实现（交给对应业务工程师）
- CI 流水线配置（交给 DevOps 工程师）
- 架构设计（交给插件架构师）

#### 调用前置条件

```
✅ 对应 DEV 任务已完成并提交 PR
✅ PR 已通过 Code Review 并合并
✅ 测试环境与目标硬件规格一致（不接受高配机替代）
```

## 三、多智能体协作调用时序

以下是第一阶段各里程碑的标准调用时序：

```
M1.0 工程规范基线
  ① DevOps 工程师     → 创建 CI 流水线、配置分支保护
  ② VS Code 插件架构师 → 初始化项目结构、配置 .gitignore
  ③ QA 测试工程师     → 验证 TEST-1.0.1 / TEST-1.0.2

M1.1 插件生命周期
  ① VS Code 插件架构师 → 实现 activate/deactivate（DEV-1.1.1）
  ② VS Code 插件架构师 → 实现 ProcessGuardian（DEV-1.1.2）
  ③ QA 测试工程师     → 执行 TEST-1.1.1a/b / TEST-1.1.2a/b

M1.2 LLM 请求队列（与 M1.3 并行）
  ① VS Code 插件架构师 → 实现 GlobalModelRequestQueue（DEV-1.2.1）
  ② VS Code 插件架构师 → 实现队列监控 Output Channel（DEV-1.2.2）
  ③ Python 工程师     → 实现 LLM 请求代理调用层
  ④ QA 测试工程师     → 执行 TEST-1.2.1a/b/c / TEST-1.2.2

M1.3 跨进程文件锁（与 M1.2 并行）
  ① VS Code 插件架构师 → 执行 PoC 验证（DEV-1.3.1）
  ② Python 工程师     → 编写 Python 侧文件锁脚本
  ③ QA 测试工程师     → 执行 TEST-1.3.1 跨进程互斥验证
  ④ VS Code 插件架构师 → 实现 FileMutex（DEV-1.3.2）
  ⑤ Node.js 工程师    → 协助跨进程集成测试
  ⑥ QA 测试工程师     → 执行 TEST-1.3.2a/b/c（三平台）

M1.4 配置与打包
  ① VS Code 插件架构师 → 实现 Settings UI（DEV-1.4.1）
  ② VS Code 插件架构师 → 打包 .vsix（DEV-1.4.2）
  ③ DevOps 工程师     → 配置 release.yml 自动发布流水线
  ④ QA 测试工程师     → 执行 TEST-1.4.1/2/3 全量验收
  ⑤ QA 测试工程师     → 填写 Exit Criteria 实测值，提交验收报告
```

## 四、智能体冲突规避规则

以下情况**禁止同时激活两个智能体**，必须串行执行：

| 冲突场景 | 原因 | 处理方式 |
|---------|------|---------|
| 插件架构师 + Node.js 工程师同时修改 `src/core/` | 文件冲突风险 | 架构师先完成接口定义，工程师再实现 |
| Python 工程师 + QA 同时运行跨进程测试 | 进程资源争抢 | Python 工程师完成实现后，移交 QA 独立执行 |
| DevOps 修改 CI + 任何工程师提交 PR | CI 配置变更中途可能导致 PR 失败 | DevOps 变更合并后，再触发其他 PR |
| 多个工程师同时修改 `phase1-task-breakdown.md` | 文档合并冲突 | 指定 QA 工程师为唯一文档维护者 |

## 五、紧急情况下的调用规则

当出现以下紧急情况时，跳过常规调用时序，直接激活对应智能体：

| 紧急情况 | 直接激活 | 授权级别 |
|---------|---------|---------|
| `main` 分支出现 Critical Bug | VS Code 插件架构师 + QA | 无需等待里程碑 |
| CI 流水线完全崩溃 | DevOps 工程师 | 无需等待里程碑 |
| 安全漏洞（密钥泄露等） | DevOps 工程师 + Node.js 工程师 | 最高优先级，立即处理 |
| 跨进程死锁导致生产阻塞 | VS Code 插件架构师 + Python 工程师 | 无需等待里程碑 |

紧急情况处理完成后，必须补充对应的 Issue 和 Post-mortem 文档。
