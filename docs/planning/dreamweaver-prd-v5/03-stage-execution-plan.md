# DreamWeaver PRD v5 分阶段执行计划

> **来源文档**: `/Users/mac/StudioProjects/storytree2/.trae/documents/多AI模型长篇小说写作平台PRD/多AI模型多分支长篇小说写作平台PRD_v5.md`
> **输出目标**: 将 PRD v5 拆解为可执行、可量化、可验收的阶段性交付方案
> **估算口径**: 以单人工作量的人天估算，默认 1 人天 = 8 小时

---

## 1. 规划原则

- 以“可上线的业务闭环”而非“纯技术堆叠”为阶段边界
- 每个阶段都必须有清晰入口条件、出口条件、核心指标与 Playwright 验收范围
- 依赖关系遵循“基础数据模型 → API/服务 → 前端交互 → 可观测性/安全 → 自动化验收”
- P0 需求优先进入前 4 个阶段，P1 Harness 与增强能力在基础闭环稳定后落地
- 涉及模型、缓存、权限、压缩的能力统一按 Harness 工程基线设计，避免后期大重构

## 4. 分阶段执行明细

### 4.1 Stage 0：基础平台与治理

**阶段目标**

- 建立 React 19 + TypeScript + Playwright + Vitest 的统一研发底座
- 完成登录注册、会话守卫、统一 API 响应、埋点与错误监控基线
- 准备好后续模块所需的数据表迁移、Mock 数据、测试夹具与权限骨架

**入口条件**

- PRD v5、已有 MVP 文档与现有测试工程可访问

**出口条件**

- 用户可以注册、登录、退出并受路由守卫保护
- 统一 API 响应格式、错误处理和埋点策略完成
- Playwright 基础夹具、测试数据、HTML/JSON 报告链路可运行

**阶段交付**

| 交付项         | 量化标准                                         | 风险                     | 应对策略                              |
| -------------- | ------------------------------------------------ | ------------------------ | ------------------------------------- |
| 认证与会话基线 | 登录/注册成功率 > 99%，鉴权接口 100% 接入守卫    | 鉴权方案前后端不一致     | 固定 JWT/Refresh Token 协议与状态码表 |
| 测试底座       | Playwright 首轮冒烟用例通过率 100%               | Mock 与真实接口字段漂移  | 先固化 schema，再生成 fixtures        |
| 监控与日志     | 核心页面、核心 API 有 traceId，Sentry 可追踪异常 | 监控接入过晚导致追查困难 | 作为 Stage 0 的完成标准强制落地       |

**技术建议**

- 会话信息、偏好设置、订阅态统一收敛到 `user_preferences` 与 auth store
- 使用 MSW 或等价 Mock 层支撑前端优先开发，但所有接口契约必须先定义
- Playwright 统一走 page object + fixture 模式，避免脚本散乱

### 4.2 Stage 1：核心创作闭环

**阶段目标**

- 完成项目、章节、写作工作台、AI 对话面板的主流程
- 提供自动保存、字数统计、模型选择、快捷续写与基础错误反馈

**入口条件**

- Stage 0 鉴权、路由守卫、测试底座完成

**出口条件**

- 作者可在工作台中持续写作，所有内容持久化成功
- AI 面板可以发起请求并显示生成结果
- 项目列表、章节切换、保存状态、异常提示均可通过 E2E 验收

**阶段交付**

| 交付项     | 量化标准                                  | 风险                   | 应对策略                                   |
| ---------- | ----------------------------------------- | ---------------------- | ------------------------------------------ |
| 工作台布局 | 首屏加载 < 2 秒，编辑输入延迟 < 50ms      | 编辑器和侧栏状态耦合   | 将项目、章节、编辑器状态拆分为独立 store   |
| 自动保存   | 防抖 2 秒，保存成功回执可视化，失败可重试 | 快速切章导致脏数据覆盖 | 保存请求附带 chapter version 与 abort 控制 |
| AI 对话    | 简单任务响应 < 3 秒，失败态可恢复         | 模型不可用导致对话阻塞 | 增加 fallback 模型与超时文案               |

**技术建议**

- 编辑器建议优先基于 TipTap/ProseMirror 实现，可扩展批注、注释、分支标记
- 自动保存与手动保存必须共享同一幂等 API，避免竞态
- 模型选择器要预留 PRD 中的中英双语模型路由策略

### 4.3 Stage 2：知识资产与分支系统

**阶段目标**

- 支持角色、世界观、伏笔、分支四类长篇小说资产
- 支持从章节内容回写结构化知识，并支持分支创建、比较与合并

**入口条件**

- Stage 1 项目、章节、编辑器闭环稳定

**出口条件**

- 作者可以在一个项目内维护角色卡、世界设定、伏笔追踪、剧情分支
- 分支创建和切换不会破坏主线数据
- 至少覆盖“创建→编辑→关联章节→查看引用→切换分支”完整验收链路

**阶段交付**

| 交付项          | 量化标准                                                  | 风险                           | 应对策略                               |
| --------------- | --------------------------------------------------------- | ------------------------------ | -------------------------------------- |
| 角色/世界观资产 | 结构化字段覆盖 PRD 核心字段 100%                          | 字段深度不足，后续 AI 无法利用 | 严格按 JSON Schema 建模                |
| 伏笔追踪        | 支持 planted/developing/payoff/verified 状态流转          | 章节引用断链                   | 以 chapterId + sourceText 双锚点记录   |
| 分支系统        | 支持 main/exploration/perspective/timeline/style 五类分支 | merge 策略复杂                 | 第一版先交付只读 diff + 人工确认 merge |

**技术建议**

- 世界观、角色、伏笔统一提供引用面板，供编辑器和 AI 面板复用
- 分支创建必须记录 fork point、父分支、章节版本链
- 先做乐观 UI，实际变更依赖服务端版本校验保证一致性

### 4.4 Stage 3：多模型智能编排

**阶段目标**

- 建立语言检测、模型路由、RAG 检索、Agent 会话、Hook 规则的完整 AI 编排层
- 支撑中文/英文写作、场景化模型选择、上下文增强和自动任务分配

**入口条件**

- Stage 1-2 的项目资产、章节数据、世界观和分支数据可检索

**出口条件**

- AI 请求可以根据语言与意图自动路由
- 检索结果、记忆、世界观、角色状态能稳定注入上下文
- Agent 模式可执行有限回合任务，Hook 管道可处理 allow/deny/modify/inform

**阶段交付**

| 交付项       | 量化标准                                         | 风险                     | 应对策略                          |
| ------------ | ------------------------------------------------ | ------------------------ | --------------------------------- |
| 模型路由     | 中/英文语言识别准确率 > 95%，回退模型命中率 100% | 单模型不可用导致业务中断 | 主模型 + fallback 双配置          |
| RAG 检索     | 相关结果 Top5 命中率 > 80%，检索耗时 < 500ms     | 搜索结果噪音大           | 关键词检索与向量检索融合重排      |
| Agent + Hook | 单任务最大回合、权限边界、超时均可配置           | 子代理无限递归           | 限制工具白名单与 generation guard |

**技术建议**

- 路由决策至少考虑语言、任务类型、成本级别、区域与隐私模式五个维度
- Hook 执行结果要形成标准化审计记录，便于后续权限/合规串联
- RAG 构建上下文时预留 Prompt Cache 分块能力，避免后续重写

### 4.5 Stage 4：Harness 工程基础设施

**阶段目标**

- 工程化落地 Prompt Cache、Permission、Memory、Compaction、Collaboration、Build 六大 Harness
- 把 PRD 中的大上下文、安全防护、记忆提取、协作代理和灰度发布能力落到可观测、可回退、可配置的服务上

**入口条件**

- Stage 3 AI 编排已稳定运行，存在足够的真实流量与日志样本

**出口条件**

- Prompt Cache 命中率、Permission 延迟、Compaction 熔断、Memory 提取、Feature Gate 灰度均有监控
- 关键失败场景具备 fail-closed、熔断或回退策略
- Harness 关键链路均可被 Playwright + API 合同测试间接验证

**阶段交付**

| 交付项            | 量化标准                                         | 风险                    | 应对策略                             |
| ----------------- | ------------------------------------------------ | ----------------------- | ------------------------------------ |
| Prompt Cache      | 正常场景命中率 > 70%，单次 bust < 20K tokens     | 分块不稳定导致持续 miss | 固化静态/动态边界与 schema cache key |
| Permission        | Stage1 P99 < 500ms，Stage2 P99 < 3s              | 审批竞态造成错误放行    | 默认 fail-closed，多竞态结果统一仲裁 |
| Compaction/Memory | 压缩失败连续 3 次后自动熔断，记忆提取最多 5 回合 | 摘要丢失关键剧情        | 保留可逆压缩记录与撤销能力           |

**技术建议**

- 将 Harness 监控指标前置建模为统一 metrics schema，避免各自为政
- Prompt Cache 与 Compaction 要共享对话上下文边界定义
- 所有 Harness 的回退路径都必须可被自动化测试触发

### 4.6 Stage 5：全球化商业化能力

**阶段目标**

- 打通 UI 国际化、双语写作、Stripe 订阅、用量计费、全球部署与区域偏好
- 让 DreamWeaver 具备全球用户可商用能力

**入口条件**

- 核心创作与 AI 工程能力已稳定

**出口条件**

- UI 可在 en/zh 间完整切换，写作语言可路由对应模型
- Stripe 订阅、续费、升级/降级、取消、退款、用量统计可通过验收
- 用户区域偏好、货币、时区、语言均能在设置中生效

**阶段交付**

| 交付项     | 量化标准                                      | 风险                   | 应对策略                                        |
| ---------- | --------------------------------------------- | ---------------------- | ----------------------------------------------- |
| i18n/l10n  | 公共页面翻译覆盖率 100%，核心工作台 100%      | 翻译 key 漏失          | 建立 key lint 与 fallback 策略                  |
| 支付订阅   | Webhook 成功率 > 99%，订阅态同步延迟 < 1 分钟 | 幂等性不足导致重复激活 | 以 stripe event id 做幂等表                     |
| 全球化偏好 | 区域、语言、货币、时区都可持久化              | 用户跨区数据规则复杂   | 先实现 region + preference，EU 数据隔离单独治理 |

**技术建议**

- UI 国际化和写作语言不要混为一谈，分别放到 `ui_language` 和 `writing_language`
- Stripe Webhook 必须支持重放和签名校验
- 全球部署方案先完成架构与回退设计，再考虑物理部署脚本

### 4.7 Stage 6：稳定性与上线验收

**阶段目标**

- 对性能、安全、合规、回归、监控告警进行总体验收
- 建立上线闸门、回归矩阵与故障演练清单

**入口条件**

- Stage 0-5 所有功能达到可演示、可联调状态

**出口条件**

- Playwright P0/P1 业务链路通过
- 安全、合规、性能指标满足 PRD 约束
- 上线 checklist、回滚策略和风险清单完成

**阶段交付**

| 交付项   | 量化标准                                         | 风险               | 应对策略                       |
| -------- | ------------------------------------------------ | ------------------ | ------------------------------ |
| 性能验收 | 首屏 < 2 秒，搜索 < 500ms，AI 简单响应 < 2 秒    | 测试环境不稳定     | 固定基准环境与数据集           |
| 合规验收 | GDPR 导出/删除、Cookie Consent、年龄确认流程闭环 | 合规流程被 UI 遗漏 | 合规模块强制进入回归集         |
| 回归体系 | P0/P1 Playwright 用例自动出 HTML/JSON 报告       | 用例波动大         | 分层 fixtures + 稳定 mock 数据 |

**技术建议**

- 将“业务冒烟、关键异常、跨语言、支付订阅、Harness 退化”设为上线必跑套件
- 关键链路加入合成监控与错误预算，避免只靠人工发现问题
- 对全球化、支付、权限、压缩等高风险能力单独维护回退预案

## 5. 风险矩阵

| 风险类型   | 风险描述                                            | 影响阶段  | 等级 | 应对策略                       |
| ---------- | --------------------------------------------------- | --------- | ---- | ------------------------------ |
| 架构风险   | AI 能力先行，Harness 后补，导致上下文与权限链路返工 | Stage 3-4 | 高   | 提前按 Harness 接口抽象实现    |
| 数据风险   | 分支、章节、世界观之间引用关系复杂，容易出现脏链接  | Stage 1-2 | 高   | 引用统一使用 UUID 与版本字段   |
| 商业风险   | Stripe 订阅状态与本地权限状态不同步                 | Stage 5   | 高   | 事件幂等、订阅态快照、补偿任务 |
| 国际化风险 | UI 文案翻译完成，但写作体验和模型路由仍是单语       | Stage 3/5 | 中   | UI 语言与写作语言双配置        |
| 测试风险   | Playwright 只验证 UI，不验证业务约束与后台状态      | 全阶段    | 中   | 每条关键用例增加 API/数据断言  |
| 性能风险   | 长文稿、深分支、复杂 RAG 导致编辑器和请求变慢       | Stage 2-6 | 高   | 大文本基准数据、分页与增量加载 |
